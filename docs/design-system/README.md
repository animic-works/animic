# Design Systemの設計資料

Design Systemの設計で得た判断材料を、次のDesign Systemでも利用できる形で残します。Animicは具体的な事例であり、その構成を他の案件へそのまま適用するためのひな形ではありません。

現在のAnimicの仕様は、既存の仕様・設計文書と実装・テストで扱います。ここでは現在値やAPI一覧を複製せず、何を比較し、何が成立せず、どの検証から判断を変えたかを扱います。

## 読み始める場所

- 今のAnimicを実装する: [ゲーム仕様](../product.md)、[デザイン原則](../design.md)、[アーキテクチャ](../architecture.md#design-system)、[実装規約](../conventions.md)、[Design Systemの変更判断](../../CONTRIBUTING.md#design-systemの変更判断)と[生成・検証手順](../../CONTRIBUTING.md#design-systemの生成と検証)。具体的なAPI・値・検査は[実装](../../packages/)と[テスト](../../tests/design-system/)を確認します。
- 重要な決定と理由を調べる: [ADR](../decisions/)。設計事例を読まなくても決定を理解できるようにします。
- 判断が変わった過程を調べる: 以下の設計事例から、必要に応じて検証記録へ進みます。
- 次のDesign Systemを設計する: [設計ガイド](design-guide.md)から問い・選択肢・判断基準を確認し、必要な設計事例へ進みます。
- 実装や設計をレビューする: [設計レビューガイド](review-guide.md)で適合性の確認と設計そのものの評価を分け、証拠の範囲と判断が必要な点を整理します。

## 文書の種類

| 種類               | 読む目的                                                                                       |
| ------------------ | ---------------------------------------------------------------------------------------------- |
| 設計ガイド         | 設計時の問い、確認する前提、選択肢、判断基準、注意点と適用条件を得る                           |
| 設計事例           | 当時の前提・比較・失敗・検証・判断変更と、変更しなかった範囲を追う                             |
| 設計レビューガイド | 適合性監査と設計そのもののレビュー、証拠の読み方、判断と実装の区別、AI利用時の判断の偏りを扱う |
| 検証記録           | 設計事例を支える入力・環境・観測結果と、その証明範囲を確認する                                 |
| 現行資料           | 現在のAnimicの要件・原則・構成・規則・API・値・手順を確認する                                  |

## 更新ルール

文書ごとの所有関係と保存・更新ルールは[CONTRIBUTINGの文書の管理](../../CONTRIBUTING.md#文書の管理)に従います。検証記録は、重要な観測事実を事例本文と分けて保存する必要がある場合に作る文書です。すべての事例に必要なものではありません。読み分ける際の要点は次のとおりです。

- 現行資料は現在の仕様・実装へ追従します。
- 設計ガイドと設計レビューガイドは、新しい知見に応じて更新できます。
- 設計事例は当時の判断過程を、検証記録は観測事実を保持します。
- 後に異なる設計を採用しても、過去の設計事例や検証記録を現行仕様へ書き換えません。事実誤認は訂正します。
