# フォントの責務分割の設計事例: デザイン判断からアセットの配信まで

フォント配置の判断と、2026-10-04時点の実装・検証を扱う事例です。判断と実装の観測を分け、根拠を[検証記録](../evidence/font-ownership.md)へ接続しています。現在のフォント一覧や読み込み手順を定める文書ではありません。

## 問い

どのフォント・太さを使うかというデザイン判断、フォントTokenに対応するアセットの解決、必要なCSSの生成、ブラウザへの配信を、どこで分けるか。すでに実装された配置がある段階でも、何を根拠に担当するパッケージを見直すか。

## 最初に一緒に置かれていたもの

当初は、ReactパッケージがFontsource依存を持ち、ReactのCSSエントリーポイントがフォントCSSとPanda生成CSSをまとめる配置だった。一方、採用するフォント・太さ・用途は`design-system`パッケージのTokenとText Styleで決めていた。

ReactのUI実装と、フレームワークに固有ではないフォント・生成CSSの配信が同じパッケージに置かれていたことが検討対象だった。フォントのデザイン判断そのものをReactへ移していた、という問題ではない。この判断変更は責務の再評価であり、フォントの読み込み障害の修正としては扱わない。

## 配置を維持する理由から、責務を分ける理由へ

次の選択肢を比較した。

| 選択肢                                                  | 当時の検討で問われたこと                                                        |
| ------------------------------------------------------- | ------------------------------------------------------------------------------- |
| React側にFontsource依存とCSSエントリーポイントを残す    | 一度のimportで済む便利さだけでなく、Reactの責務として自然か                     |
| `design-system`パッケージからフォントアセットも提供する | デザイン定義と近くなる一方、実行時アセットの配信まで定義側へ加えることになるか  |
| styled-systemからフォントCSSとPanda CSSを提供する       | CSSの配信をまとめられるか。フォント・太さの別一覧を手作業で持つことにならないか |
| `design-system`パッケージの定義から必要なCSSを生成する  | 判断の重複を避けられるか。そのための生成処理が過大にならないか                  |
| Pandaの関連機能を使う                                   | 機能の存在ではなく、責務分担を単純にできるか                                    |

一度は、React側の配置を維持し、整合検査を加える案を採ろうとした。しかし、まだ公開・運用されていないAPIについて、既存配置、import先、変更量、互換性を維持することを現状維持の根拠から外した。

未公開・未運用のAPIについて既存配置との互換性を設計上の制約にすると、今どこがフォントを配信するべきかではなく、すでにどこに実装したかで責務が決まってしまう。この訂正によって、配置を置き換えられる前提で比較し直し、styled-systemからの提供と、Text Styleからの生成を組み合わせる判断になった。

これは公開利用者への破壊的変更が起きた事例ではない。各案を実装して速度や保守コストを測り、優劣を決めた記録でもない。未公開という前提を確認して、設計の判断基準を訂正した事例である。

## フォントを選ぶ判断と、アセットへ対応付ける情報

フォントの利用判断は、用途ごとにフォント・太さを選ぶText Styleと、その参照先のTypography Tokenに残した。フォント配信を移しても、採用フォント・フォールバックフォント・太さを改めて選び直すことはしなかった。

Fontsourceへ接続するには、フォントTokenがどのパッケージを指すかという情報が別に必要だった。そのための`font-assets.ts`は非公開の対応表とし、用途や必要な太さの一覧を加えなかった。対応表へそれらを加えると、Text Styleと対応表の両方で「何を使うか」を決めることになるためだった。

必要なフォント・太さの組はText Styleから導出することにした。生成処理は、その組をTokenとアセット対応から解決し、対応するFontsource CSSが存在することを確認してimport文を作る。結果として必要な組が少数でも、その一覧を生成スクリプトに直接書く方針は採らなかった。

2026-10-04の実装確認では、対応表はパッケージ名だけを持ち、生成処理はText Styleを走査していた（[FO-E02](../evidence/font-ownership.md#fo-e02)）。これは最初から分離が完成していたという説明ではなく、配置の再評価に伴って具体化した判断である。

## CSSを届ける責務をReactから分ける

Animicでは、styled-systemが生成されたSDKとCSSを提供し、ReactがDOM・ARIA・操作を担当する分担を採っていた。フォントCSSはReact固有の処理ではなく、ブラウザへ届けるCSSの一部として扱える。そのため、Fontsource依存はアセットを解決して配信するstyled-systemが持つことにした。

公開CSSエントリーポイントもstyled-systemへまとめ、React側にはフォント依存やCSSエントリーポイント、旧エントリーポイントの互換aliasを残さなかった。将来の別フレームワークを想像しただけの変更ではなく、当時すでに分けていた「デザイン定義」「生成SDK・CSS」「React実装」の責務へ配信を合わせたものだった。

生成処理はリポジトリ側から`design-system`パッケージの定義を読み、styled-systemの成果物を書く。この生成時の関係を理由に、styled-systemから`design-system`パッケージへの実行時依存を追加しなかった。2026-10-04に確認した依存定義・CSSエントリーポイント・生成コマンドは、この判断と一致していた（[FO-E03](../evidence/font-ownership.md#fo-e03)）。

Fontsourceの`@font-face`・`unicode-range`・バイナリはそのまま利用した。Animic側で作るのは必要なCSSを選ぶimport文であり、フォント配信の中身を再実装する処理ではない。Pandaの`globalFontface`へ定義を複製する方式も採らなかった。これは判断した範囲での選択であり、その機能を使う案が技術的に失敗した結果ではない（[FO-E02](../evidence/font-ownership.md#fo-e02)）。

## 分けた責務を、何で確かめたか

固定したimport一覧が一度生成できるだけでは、デザイン判断の重複を避けたことの確認にはならない。既存テストは、Text Styleの追加・削除・太さ変更に出力が追従すること、同じ組を重複させないこと、解決できないToken・対応情報・提供されない太さを例外として検出することを扱っていた。

2026-10-04の契約テストでは、既存のフォントCSSと生成関数の結果の一致、Reactの旧CSSエントリーポイントやアセット対応表が公開されていないことも確認した。この成功を、変更前の実装も同じだったという証拠にはしない（[FO-E04](../evidence/font-ownership.md#fo-e04)）。

配置変更後の検証では、生成先を空にして、フォントCSSを含む成果物が一致することを確認した。また、単一CSSエントリーポイントを使うフォントのブラウザテストも成功した。前者はファイルの再現、後者はブラウザ検査の結果であり、互いの代わりにはならない。これらは上記の契約テストとは別の検証である（[FO-E05](../evidence/font-ownership.md#fo-e05)、[FO-E06](../evidence/font-ownership.md#fo-e06)）。

## 変更したものと、維持したもの

Fontsource依存とCSS配信を担当するパッケージをReactからstyled-systemへ変更し、必要なCSSは別の一覧に固定せずText Styleから導出することを明示した。この変更は、薄いアセット対応表、生成処理、styled-systemのCSSエントリーポイント、生成フローと検証への統合として具体化した。

一方、採用フォント・Typographyのデザイン判断、3パッケージの基本的な分担、ReactがDOMと操作を担当する方針は維持した。Fontsource自体のCSSとフォントファイルも再生成しなかった。パッケージの公開・取得方式はこの判断に含めなかった。

## 別の設計へ持ち出せる判断材料

以下は、この事例を後から整理した問いであり、すべてのデザインシステムに同じ配置を勧めるものではない。

- 現状維持の理由に互換性を挙げる前に、公開済みのAPIと利用者が実際に存在するかを確認する。この事例での訂正は未公開という前提に依存し、公開済みAPIの互換性を軽視する理由にはならない。
- フォントを使う判断、アセットへの対応付け、ブラウザへの配信は、変更理由が同じかを分けて考える。Animicでは既存のパッケージ分担へ収められたが、別案件にも同じ3パッケージが必要だとは示していない。
- 必要なアセットを既存定義から導ける場合、生成処理が別のデザイン一覧を持っていないか確認する。この限定的な生成処理の成立は、どんな定義でも自動生成すべきという根拠ではない。
- どのパッケージが定義・実装を持つか、定義変更への追従、空の生成先からの再現、ブラウザへの配信は別々に確かめる。一つのテスト成功だけで全部を保証したことにしない。

## 記録上の限界

配置を維持する案と判断基準の訂正は、設計時の比較に基づく。各案を実装して性能・保守コストの優劣を測った結果ではなく、公開利用者の互換性問題やフォント読み込み障害を修正した事例でもない。

契約テスト、再現性検証、ブラウザテストは対象が異なり、一つの成功で他の成立まで保証するものではない。各結果の証明範囲は[フォントの責務分割の検証記録](../evidence/font-ownership.md#記録上の限界)を参照する。
