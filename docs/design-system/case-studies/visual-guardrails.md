# Visual / Guardrailの設計事例: 表現の責務と、実際に成立する利用形式

対象は2026-10-04に確認した問題と、それを受けた許可形式・検証方法の変更です。当時のレビューで比較した案と承認された判断を整理し、観測事実は[検証記録](../evidence/visual-guardrails.md)へ接続しています。現在の実装手順やAPI一覧を定める文書ではありません。

## 問い

機能固有のアートワーク・演出と、それらに必要な位置・寸法の指定を許可しながら、通常UIの再構築を防ぎ、許可した記述がGuardrailだけでなくTypeScript・Panda生成・ブラウザまで実際に成立する形を、どう定めたか。

## 前提

通常UIはDesign SystemのComponentやPatternを組み合わせ、画面側から低レベルのスタイル指定を自由に行わない方針だった。一方、固有のアートワーク、特殊な配置、画面遷移、機能固有のMotionには、共通UIの選択肢だけに収まらない表現を必要とした。

固有表現を扱う限定領域としてVisualを設けることが決められていた。位置・寸法など、その表現に固有の値を扱えるようにする一方、Button・Surfaceや色・Typography・余白の体系を作る第二の入口にはしなかった。共通Motionと機能固有のMotionの配置も分けた。

この事例はVisualの設置を前提とし、その利用形式を具体化した判断を扱う。現在の責務と利用形式は[アーキテクチャ](../../architecture.md#機能固有のvisual)が説明する。

## 最初に許可していた形式

調査時のGuardrailは、Visualに対して`css`のインポートを許可し、その直接呼び出しの引数を静的に確認できる位置・寸法などの指定へ制限していた。余白Tokenと負の派生値の流用を拒否する検査もあった。一方、Visualの`className`は通常UIの禁止属性から除外され、値の生成元までは確認していなかった。

機能固有のKeyframesはVisualで扱う方針だったが、許可するスタイリングAPIは`css`のみだった。検査はそのオブジェクト内の`@keyframes`・`from`・`to`等を受理していた。この状態は当時のソースコードの読み取り結果と検証用コードから確認したもので、修正後コードから過去を推定したものではない（[VG-E01](../evidence/visual-guardrails.md#vg-e01)、[VG-E04](../evidence/visual-guardrails.md#vg-e04)）。

## クラスの生成元という抜け道

Surfaceのクラスを任意に付けたTSXは、旧Guardrailで診断されなかった。これとは別にブラウザで検証したところ、同じクラスを普通の`div`へ付けると、Surface相当の余白・境界線・影・角丸が適用された（[VG-E01](../evidence/visual-guardrails.md#vg-e01)）。

ここで行ったのは二つの個別検証であり、Guardrailへ渡したTSXをそのままビルドした一貫したE2E検証ではない。また、実際の機能で起きた障害でもない。それでも、クラスの入力を検査しないことと、同じクラスで通常UIを表示できることの両方を観測できた。

呼び出している関数が`css`由来かどうかを確認する検査にも抜けがあった。`css({ p: "5" })`は拒否される一方、`const draw = css`の後に`draw({ p: "5" })`を呼ぶ入力は通った。旧Guardrailはインポートした識別子への直接呼び出しを検査しており、この別変数経由の呼び出しはその対象から外れた（[VG-E02](../evidence/visual-guardrails.md#vg-e02)）。

プロパティの許可リストは、検査対象になったスタイルの内容を制限していた。しかし、クラスがどこから来たか、呼び出した関数が検査対象として認識されるかは別の問題だった。別変数経由ならすべてのスタイル指定を迂回できると実証したわけではない。

## 解析を広げるか、利用形式を狭めるか

検査漏れの修正に際し、当時のレビューでは次の二案を比較した。

| 当時の提案                           | 利点                                                           | 制約・懸念                                                                                 |
| ------------------------------------ | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 参照・aliasの追跡を広げる            | 関数やオブジェクトを使ったクラス生成・合成の自由度を保てる     | 戻り値・関数引数・別ファイル等へ解析範囲が広がる。その自由度を必要とする実装は当時なかった |
| 局所的に確認できる利用形式へ限定する | 検査範囲を限定し、生成処理でも成立するコード形式を確認しやすい | 許可形式外の合成は拒否し、必要になれば再判断する                                           |

採用したのは後者だった。検査済み`css()`の直接利用と、同一ファイルの単純な`const`の参照を成立させ、任意のクラス、未知の関数の戻り値、インポートしたクラス、`css`関数自体の代入・受け渡しを許可しないことにした。import宣言で指定するaliasは、生成元を直接確認できるため許可した。

条件付きクラスの合成を許可する仕組みは、この時点では決めなかった。検査では拒否し、実際に必要になった時点で判断することとした。動的なアートワークに必要な自由度をすべて満たすと証明したわけではない。

これは提案と判断の記録である。汎用的なデータフロー解析器を実装して、保守コストや性能を比較した結果ではない。検査漏れ自体の修正と、利用者へどのJavaScript形式を許可するかの判断を分けた。

## Guardrailを通ってもフレームワーク上で成立しない

### 位置・寸法の直接指定

旧許可テストには`top: "-5px"`があった。Guardrailはこの入力を受理したが、実際のTSXとして型検査するとTS2769になった（[VG-E03](../evidence/visual-guardrails.md#vg-e03)）。

テストが扱っていたのはコード文字列であり、プロジェクトの型チェックは文字列内部をTypeScriptコードとして検査しない。Guardrailテストと通常の型チェックが成功していても、その許可例が型付きSDKで記述できることにはならなかった。

### `css()`内に直接書くKeyframes

`css()`内へ`@keyframes`を書いた入力もGuardrailを通った。しかしTypeScriptは未知のプロパティとして拒否した。Pandaの生成コマンドは成功してCSSを出力したものの、フレーム内は期待するKeyframes構造にならず、ブラウザCSSOMで対象規則のフレーム数は0だった（[VG-E04](../evidence/visual-guardrails.md#vg-e04)）。

この結果を「生成コマンドが失敗した」「CSSが生成されなかった」とは扱えない。生成物は存在したが、有効なフレームを持つという目的を満たさなかった。

## Pandaの型・生成の仕組みに合わせる

位置・寸法は`top: "[-5px]"`というPandaのarbitrary value構文に合わせると、Guardrail・型・生成が成立した。その表現に固有の位置・寸法を禁止したり、strict設定を緩和したりする必要はなかった。デザインで定めた余白Tokenや負の派生値を利用する方針へ変えたわけでもない（[VG-E03](../evidence/visual-guardrails.md#vg-e03)）。

Keyframesについては、当時のレビューで別の二案を比較した。

| 当時の提案                                                   | 利点                                                  | 制約・懸念                                                 |
| ------------------------------------------------------------ | ----------------------------------------------------- | ---------------------------------------------------------- |
| `css`のみの制限を維持し、固有Keyframesは未対応として保留する | 許可APIを増やさない                                   | 「Visualで扱える」という説明と対応範囲を訂正する必要がある |
| 同じエントリーポイントの`keyframes()`を限定利用する          | Pandaの生成処理を使い、機能側で固有Motionを所有できる | 静的なフレーム定義と生成名の局所参照を検査する必要がある   |

比較した`keyframes()`の試作コードでは、最初の`animationName: spark`もstrictな型制約に合わなかった。生成名を ``animationName: `[${spark}]` `` として渡す形式へ修正すると、型・生成・CSSOM上の2フレームが成立した。ただし、この調査時点では旧Guardrailが`keyframes()`のインポート等を拒否していた（[VG-E05](../evidence/visual-guardrails.md#vg-e05)）。

採用したのは`keyframes()`の限定利用だった。フレーム内にもVisualの表現範囲を適用し、生成名は同じVisual内の検査済み`css()`から参照する形にした。誤った直接記述形式を拒否するだけで終わらず、承認していた機能固有のMotionの経路を成立させた。

機能固有のKeyframesを共通Design Systemへ移す案は、責務を変えるため推奨されず、移動しないことが確認された。この構成では、独自Guardrailの許可形式とPandaで型チェック・CSS生成が通る形式を一致させるためにPanda固有APIを選んだ。

## 検証方法を接続する

修正後はVisualのストーリーを一つ用意し、Guardrailがそのソースコードを読み、同じファイルをTypeScript・Panda生成・ブラウザでも使用する形にした。Guardrailへは機能固有のVisualの仮想ファイル名として渡しており、実際の機能へ演出を追加したものではない。

| 層              | 確認したこと                                                                             | 単独では確認できないこと               |
| --------------- | ---------------------------------------------------------------------------------------- | -------------------------------------- |
| Guardrail       | 許可したコード形式と表現範囲                                                             | 型・生成・表示の成立                   |
| TypeScript      | strict設定を有効にしたSDKで記述できること                                                | CSSのブラウザ解釈                      |
| Pandaによる生成 | 必要な位置・寸法・Keyframesの出力                                                        | 実要素へ適用された結果                 |
| ブラウザ        | computed styleの位置・寸法、実要素のアニメーションのフレーム、reduced motion設定での停止 | ほかの機能固有の表現も十分に扱えること |

実要素の`CSSAnimation`からフレームを取得し、reduced motion設定へ環境を変えたときの停止も確認した。調査段階のCSSOM確認から、実要素の動作確認へ検証対象を広げたことになる（[VG-E06](../evidence/visual-guardrails.md#vg-e06)）。

既存の画像比較テストも通ったが、このVisualのストーリー自身には基準画像を設けていなかった。画像比較で固有演出の見た目を承認した結果ではない。

## analyzeの0をどう扱ったか

修正後の`panda analyze`ではKeyframesの使用数と重複を除いた件数が0だった。一方、生成CSSとブラウザではVisual内のKeyframesが成立していた。この集計だけで機能不成立とはせず、型・生成物・実要素のアニメーションの検証を成立根拠にした（[VG-E07](../evidence/visual-guardrails.md#vg-e07)）。

0になった内部原因は確定していない。analyzeの不具合や、`keyframes()`を常に集計しない仕様と断定したわけではない。

Motionの配置を維持する判断は、この集計結果より先に決まっていた。0を見てからアーキテクチャを比較し直した記録はなく、集計を増やすために固有Motionを共通定義へ移す修正も行わなかった。

## 変更したもの

**設計判断:** クラスの自由度を任意文字列ではなく検査可能な生成形式として定め、`keyframes()`による静的Keyframesと局所参照を許可した。位置・寸法の直接指定はPandaのarbitrary value構文で扱うことを具体化した。

**実装修正:** インポートした識別子・`const`の初期値・利用箇所を確認するGuardrailへ改め、`css()`内にKeyframesを直接書く誤った形式を拒否した。許可・拒否テストを修正し、同じストーリーを型・生成・ブラウザへ接続した。アーキテクチャ文書の利用形式の説明も、この判断に合わせて更新した。

変更対象の記録では、Visualに関係する変更はGuardrail、契約テスト、Visualのストーリー、ブラウザテスト、アーキテクチャ文書だった。これらの実装・検証の対応は[VG-E06](../evidence/visual-guardrails.md#vg-e06)に整理している。

## 変更しなかったもの

判断の際には次を維持することも明示された。

- デザイン定義、生成SDK・CSS、React実装という3パッケージ構成と依存方向・`exports`。
- 機能固有のVisualという領域自体と、既存の`@animic/styled-system/css`エントリーポイント。
- `strictTokens`・`strictPropertyValues`。
- 通常UIとVisualの責務分離。デザインで定めた余白やその負の派生値をVisualの位置・寸法へ流用しない方針。
- 共通MotionはDesign System、機能固有のアートワーク・演出・Motionは機能側で所有する方針。
- Guardrailで利用境界を検査する方針。

新しいパッケージ・ラッパー・独自の生成処理で不足を埋めることもしなかった。変更したのは、これらの責務を実現する利用形式と検証の接続であり、問題の発見を理由にアーキテクチャ全体を再設計したわけではない。

## この事例から得られること

以下は観測と判断を後から整理したものであり、当時測定した一般法則ではない。

- 検査対象のプロパティを制限することと、そのクラス・関数の生成元を確認することは別だった。許可範囲を守るには、どの経路で表現が届くかも確認する必要があった。
- 解析を広げる以外に、必要なコード形式を限定する選択肢があった。ただし長期保守コストの優劣は実測しておらず、必要な自由度が異なる案件へ同じ制限をそのまま適用する根拠にはならない。
- Guardrailの許可例を同じ入力のまま型・生成・ブラウザへ接続することで、独立した検査だけでは残った不整合を確認できた。一つのストーリーで全利用方法を保証したわけではない。
- ツールの成功や集計値は、そのツールが確認した範囲の証拠だった。生成コマンドの成功やanalyzeの0だけで、ブラウザ上の成立を判断できなかった。

## 限界

問題は実際の機能ではなく監査用の検証コードで見つかり、任意のクラスのGuardrail・ブラウザ確認は別々の検証だった。汎用的なデータフロー解析器の実装・性能比較は行っていない。

`keyframes()`の試作コードは修正前後で入力が異なり、旧Guardrailの拒否結果は修正後の入力に対する結果ではない。調査時のKeyframes確認はCSSOMで、実要素のアニメーション確認は修正後ストーリーによる。Visualのストーリー自身の基準画像はなかった。analyzeが0になった内部原因は確定していない。詳細は[証拠全体の限界](../evidence/visual-guardrails.md#証拠全体の限界)を参照する。
