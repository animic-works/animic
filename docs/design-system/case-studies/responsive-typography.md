# Responsive / Typographyの設計事例: 意味を保って構成を変える

2026-10-04までのレスポンシブとTypographyの判断、文字拡大時の測定を扱う事例です。幅に応じた構成とTypographyをどう分け、特定のレイアウトでの表示崩れをどこで解決したかを扱います。現在の条件値やText Style一覧は[現行資料](#現行資料)を参照してください。

## 問い

利用できる空間が狭くなったとき、文字や操作領域を縮めず、情報の意味とDOM順を保ったまま構成を変えられるか。表示が収まらない場合、共通Typographyを変える必要があるのか、それとも組み合わせる側の選択で解決できるのか。

## 端末の分類より、構成が成立する領域を見る

Animicのデザイン原則は、画面サイズに応じて配置や構造を変えても、操作・状態・情報の意味を不用意に変えないことを求めていた。狭い画面へ収めるために可読性や操作領域を犠牲にしないことも前提だった。

幅条件は最初から一律に決まっていたわけではない。承認文面では、長いラベル、入力エラー、複数列、Dialog、文字拡大で成立を確認してから条件を決める順序が指定されていた。`base`は条件のない既定値であり、特定の端末名を表すものとはしなかった。

採用したのは、Grid・Splitが自身に与えられた利用可能幅をContainer Queryで判定する方式だった。ビューポートが広くても、別の領域内に置かれたGridが同じ幅を使えるとは限らない。配置を変える判断を、実際に配置を成立させる領域へ対応付けた。

Gridは狭い領域で1列、中間で最大2列、広い領域で要求された列数を使う。Splitは縦並びから等幅または非対称の横並びへ変わるが、DOM順は変えない。同じ幅条件を使う場合も、値が共通だから採るのではなく、その構成で成立を確認したから再利用する整理だった。

当時承認した30em / 54emは、この確認対象で使う条件であり、Design System全体の端末分類にはしなかった。`equal` SplitはGridの2列と似ていることだけでは確定せず、専用測定を確認した後の承認文面で条件が確定している。

## Dialogの表示形態と、内容のレイアウトを分ける

Dialogでは、狭い利用可能幅で下端表示、成立する幅で中央表示へ変わる`adaptive`と、常に中央表示する`centered`を分けた。クエリコンテナはビューポート全体を占める位置決め用要素であり、Grid・Splitと同様に任意の幅条件を利用側へ公開しなかった。

下端表示の採用は、狭い幅での実表示を確認した承認に基づく。上部の形状を保ち、横方向の空間を使い、内容が高ければDialog内部をスクロールさせる方向だった。TypographyやControl寸法を縮小して合わせる判断ではない。

一方、操作ボタンのレイアウトは、Dialogの表示形態が変わることとは別だった。比較ストーリーのボタンは呼び出し側のClusterで組み合わせており、Dialogの`presentation`に連動して配置を変更する責務は加えなかった。この分離は、同じ内容を保ったまま表示位置を切り替える検証にも残した。

## 文字の用途、HTMLの意味、外側の余白

Typographyは、フォント・文字サイズ・太さ・行間を画面ごとに組み合わせる方式ではなく、用途を持つText Styleで選ぶことにした。Textは用途の`variant`と意味に応じた`tone`を持つ。HeadingはHTMLの見出しレベルと表示サイズを別の判断とし、両方を明示させた。大きく表示したいことだけを理由に文書構造まで変えないためだった。

ブラウザのデフォルトスタイルのリセットも、デザイン上の配置とは分けた。Text・Headingの`margin: 0`はHTML要素の既定余白を消すReact側の処理として残し、外側の間隔はPatternと画面の組み立てで決めることにした。Text Styleへ余白判断を移さなかった。

`font-synthesis: none`はText・Headingごとの指定から、AnimicのUIへ基礎設定を適用する範囲へ移した。Portalではその範囲外にも基礎設定を持たせた。適用範囲と外部の文書への影響は[Interaction / Environmentの設計事例](interaction-environment.md#適用範囲とportalを一緒に扱う)で扱う。

この時点では、幅に応じた文字サイズ変更を設けなかった。また、Text・Headingすべてへの`overflow-wrap: anywhere`は、本文・見出し・コード・数値を同じ改行規則にする強い判断として採用せず、共通指定から外した。代わりにcode・numericを一律`nowrap`にすることもせず、通常のCSSの改行規則へ任せ、具体的な用途で問題が出たらその用途を確認することにした。

## 8文字コードの問題を、Surfaceの選択で解決する

共通の折り返し指定を外した後、既存の幅条件を変えずに再検証することが求められた。当時の測定では、320pxのビューポートと文字サイズ200%で、8文字コード`ABCD2345`がSurfaceの内容領域より広くなっていた。ページの横スクロール幅だけを見れば320pxのままだったため、ページ全体のoverflow検査だけでは内部のはみ出しを見落とす状態だった。

比較用のブラウザ操作では、既存のSurfaceの`padding="compact"`に相当するクラスへ切り替えると、文字のフォント・サイズ・字間を変えずに内容領域へ収まった。別の調査では`overflow-wrap: anywhere`を一時的に付けると折り返して収まったが、それを共通Typographyへ戻す決定はしなかった。

採用したのは、対象の組み合わせ側で既存の`Surface padding="compact"`を明示する修正だった。Surfaceの既定値を変えたり、狭い幅になると自動的に余白を減らしたりする挙動は加えなかった。codeの文字サイズや改行規則、既に承認した幅条件も維持した。

比較した入力と修正後の結果は次のとおりである。数値は当時のChromiumでの観測であり、現在の寸法仕様ではない。

| 確認             | 入力と観測                                                                                                                                     | 検証方法・範囲                                                                      |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| はみ出しの確認   | Gridの2列、equal Split、main-asideのストーリー。320px・文字サイズ32pxで、コードの領域幅158pxに対し文字幅182.734375px、ページ幅320px            | この個別測定から全配置の不成立は断定しない                                          |
| 既存余白の比較   | equal Split、320px・文字200%。通常余白では領域幅158px、compact相当へ切り替えると190px。文字幅は両方182.734375px                                | フォントを明示的に読み込んだブラウザ上のクラス差し替えであり、修正後TSXの検証とは別 |
| 組み合わせ修正後 | Gridの1〜4列、equal・main-aside・aside-mainの7ストーリー。320px・文字200%でページ幅320px、各コードの文字範囲がSurfaceのpaddingを除く内容領域内 | コードのフォントを読み込み、DOM Rangeと内容領域を比較                               |
| 既定余白の維持   | 320pxと1000pxの双方で、文字サイズ16px時の既定paddingは24px、32px時は48px                                                                       | この組み合わせで幅による自動切り替えがないことを確認                                |

## 条件の境界と、内容領域まで検査する

現在の[境界テスト](../../../tests/design-system/browser/focus-responsive.spec.ts)は、文字サイズ16px・32pxで条件の直前・一致・直後を調べる。Grid・Splitでは広いビューポートの中でコンテナ幅を変え、入れ子のGridも自身の幅で変化することを確認する。列数だけでなくDOM順、Splitの間隔、非対称の比率も検査対象になっている。

Dialogでは表示位置の切り替えと、呼び出し側が組み合わせた操作ボタンの配置を別々に検査する。320px・文字200%のケースでは、文字を縮めず、内部スクロールで操作まで到達できることを確認する。

コード表示にはページ全体の横幅に加え、実際の文字範囲がSurfaceの内容領域を越えていないことを検査するテストが追加された。任意の長さの文字列が収まる証明ではなく、承認時に問題となった入力の再発を検出するための確認である。

修正後の検証では、境界・文字拡大テストも成功した。その結果と現在の検査内容は区別し、過去の成功が将来の変更後も成立する保証とは扱わない。

## 維持した境界と、別の設計で使える問い

この過程で具体化・修正したのは、利用可能幅に応じる構成、Typographyのデフォルトスタイルをリセットする場所、共通の折り返し指定の撤回、特定の組み合わせにおける余白の選択だった。DOM順、見出しの意味と見た目の分離、Typography・操作領域を狭さに合わせて縮めない方針は維持した。コードの問題を理由に条件値やSurfaceの既定値を再設計しなかった。

後からこの事例を判断材料として整理すると、次の問いが得られる。

- 変える必要があるのは情報の意味か、それとも並びや構造か。
- 幅条件はビューポート全体に属するか、配置を成立させる個別領域に属するか。
- 値が共通だから条件を再利用するのか、同じ成立条件を確認したから再利用するのか。
- HTML要素のデフォルトスタイルのリセットと、画面上の余白・見出し階層の判断を混ぜていないか。
- はみ出しを見つけたとき、共通Typographyを変える前に既存の選択肢で組み合わせを成立させられないか。

これらは当時の観測から整理した問いであり、任意のoverflowを余白だけで解決する規則ではない。Animicの条件値を別案件へ移す根拠にもならない。

## 記録上の限界

具体的なはみ出しの観測は8文字コードの記録であり、numeric全般の成立・不成立を示すものではない。文字200%はルートの文字サイズを変更した検証で、ブラウザの全ズーム方式・全フォント・全言語での成立を示さない。

本文の順序は判断対象ごとの整理であり、すべてが一度の連続した実験で決まったことを意味しない。現在のリンク先が変わっても、ここに残した当時の観測と判断は現行仕様へ同期しない。
