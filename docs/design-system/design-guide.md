# デザインシステムの設計ガイド

デザインシステムを設計するときに、何を問い、どの前提を確認して選択するかを整理したガイドです。Animicの[Visual](case-studies/visual-guardrails.md)、[フォント](case-studies/font-ownership.md)、[Responsive / Typography](case-studies/responsive-typography.md)、[Interaction / Environment](case-studies/interaction-environment.md)の事例を判断材料にしています。同じパッケージ数、API、制限、幅条件を他の案件へ適用するための仕様書ではありません。

現在のAnimicを実装する場合は[アーキテクチャ](../architecture.md#デザインシステム)と[実装規約](../conventions.md)、変更の実務手順は[CONTRIBUTING](../../CONTRIBUTING.md#デザインシステムの変更判断)を参照してください。既存の設計を評価する進め方は[設計レビューガイド](review-guide.md)で扱います。

## 最初に、誰の何の判断を支えるか

必要な画面、利用者、実装環境と、利用側へ委ねたい判断を確認する。見た目の統一だけでなく、操作・状態・アクセシビリティまで共有するのかを明らかにすると、デザインシステムとComponentライブラリを同じものとして扱わずに検討できる。

まだ利用例がない自由度と、すでに必要な自由度を分ける。不足が確認できない段階で新しいToken、Component、例外経路を先に増やさない。

## 既存定義で表現できない場合の判断

まず、何が成立しないかを内容・状態・操作・利用可能な幅などの具体例で示す。必要な表現に対応する定義と公開APIを調べ、単独のComponentに選択肢がないことと、既存の組み合わせでも表現できないことを分ける。

| 確認すること                                                       | 判断の方向                                                                                                      |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| 既存の公開APIの選択や組み合わせで成立するか                        | 利用側の構成を変え、デザインシステムは変更しない                                                                |
| 不足しているのは、その画面だけの業務上の構成か                     | アプリケーション側で組み立てる。共通Componentへ機能固有の条件を積み上げない                                     |
| 共通する意味・状態・操作・アクセシビリティ上の表現が不足しているか | デザインシステムの変更候補として扱う。同じ見た目や値の出現だけを追加理由にしない                                |
| 必要なのは機能固有のアートワーク・配置・演出か                     | [例外領域の責務](#例外領域は必要な表現と検査可能な形式から考える)に該当するか確認する。通常UIの不足とは区別する |

デザインシステムを変える必要がある場合は、[変更理由ごとの責務](#表現の責務を変更理由から分ける)から変更先を選ぶ。基礎値・用途の意味ならToken、表現単位ならStyle、variant・状態ならRecipe、配置関係ならPattern、DOM・操作・ARIAならReact等のフレームワーク実装を検討する。既存の公開APIで足りるかは[公開APIの判断](#公開apiで何を利用側に選ばせるか)と合わせて確認する。

任意CSSや自由なクラスを追加して利用境界を迂回することは、不足の解決とは扱わない。Visualのような限定領域も通常UIを作り直すための入口ではない。現状維持を正式な選択肢に含め、新しい意味・公開範囲・条件を選ぶ必要があれば、実装の前に判断を分けて提示する。

## 表現の責務を、変更理由から分ける

デザイン上の判断、アセット解決、CSSの配信、DOMと操作、画面の組み立ては、同じ理由で変わるとは限らない。まずそれぞれの変更がどこへ及ぶかを調べ、分ける必要がある単位を選ぶ。

| 問い                                                 | 選択肢と判断材料                                                                                                                                                                |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| デザイン定義とフレームワーク実装を分ける必要があるか | 同じ場所で扱う方が自然な規模・用途もある。DOMやライブラリの都合と独立して定義を変えたい、定義を複数の実装で使う等の理由があるなら分離を検討する。パッケージ数自体を目標にしない |
| PrimitiveとSemantic Tokenで何を分けるか              | 基礎値と用途の意味が別なら分ける。同じ色や寸法でも役割が異なる場合、値の一致だけで意味を統合しない。反対に、役割を説明できないSemantic Tokenを網羅的に増やさない                |
| Style・Recipe・Pattern・Componentのどこへ置くか      | 文字や面などの表現単位、variant・スロット・状態、配置の関係、DOM・操作・ARIAのどれが変わるのかを見る。値の置き場だけでなく、その変更を検証する場所まで確認する                  |
| 機能固有表現を共通化するか                           | 意味・状態・操作・アクセシビリティ上の責務が共通なら共通定義を検討する。単に同じ値が出た、ある機能だけの演出を収めたい、という理由なら機能側の組み合わせや限定領域も比較する    |

共通Componentへ機能名による条件分岐が積み上がる、DOMの修正だけでデザイン定義まで変わる、生成処理にも同じ値一覧が必要になる、といった状態は定義・実装の配置を確認するきっかけになる。それだけで分離が誤りと断定せず、実際の変更経路をたどる。

[フォントの事例](case-studies/font-ownership.md#フォントを選ぶ判断とアセットへ対応付ける情報)では、用途・太さの選択と、Fontsourceへの対応付け、生成、配信を分けた。この分離の理由は再利用できるが、Animicの3パッケージ構成まで一般化する必要はない。

## 公開APIで、何を利用側に選ばせるか

自由なCSS指定と用途ごとの選択肢では、利用側が負う判断が異なる。画面側で視覚表現を自由に変える必要があるのか、承認済みの表現から意味を選べればよいのかを先に確認する。任意値を受けないAPIにする場合も、実際の利用例を成立させられることが条件になる。

- 進捗率や選択値など、実行時に変わる情報は何か。意味のあるpropsとして受け、内部でCSS変数等へ対応付けられるか。
- Headless UIの型、ストア、Anatomy、状態変更通知の詳細を、そのまま公開する必要があるか。独立したAPIは接続実装を必要とする一方、内部ライブラリの都合と利用側の判断を分けられる。
- HTMLの意味と見た目は同じ判断か。見出しレベルと表示サイズのように別の理由で選ぶものを、自動的に対応付けていないか。
- 設計上重要な選択を既定値で隠していないか。反対に、安定した既定値で足りる選択まで必須にしていないか。

公開境界は一つの検査で完結させず、目的を分ける。

| 仕組み                      | 受け持つ判断                                                                                                             |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| パッケージの`exports`       | そのパッケージの公開エントリーポイント。直接利用する必要のない内部構造は、検査で禁止できるからという理由だけで公開しない |
| 公開propsの型               | 利用可能な値と組み合わせ。型のない呼び出しや外部CSSまで防ぐものではない                                                  |
| インポート・構文の検査      | 公開されたエントリーポイントをどの場所・形式から利用してよいか                                                           |
| 実行時のpropsフィルタリング | 型を迂回して渡された余分な値を、DOM等へ通さない必要がある場合の処理                                                      |

一般的なpropsの組み合わせと、任意のスタイル指定による迂回も区別する。JSX spreadを制限するなら、何が含まれるか分からない入力を拒否したいのか、spreadという記法自体を禁じたいのかを明らかにする。Animicでの閉じたprops型の検査を、すべての案件の必須方式にはしない。

## 例外領域は、必要な表現と検査可能な形式から考える

機能固有の表現に限定領域が必要なら、その領域が扱う責務を説明する。装飾配置や固有Motionを許すことと、通常UIの色・余白・Surfaceを自由に作り直せることは別である。

[Visualの事例](case-studies/visual-guardrails.md#クラスの生成元という抜け道)では、プロパティの許可リストがあっても、任意のクラスや検査対象外の関数呼び出しという経路が残った。制限する値だけでなく、値・クラスがどこから届くかを確認する必要があった。

生成元の追跡を広げるか、局所的に確認できるコード形式へ限定するかは、必要な自由度によって選ぶ。関数・別ファイル・条件合成を実際に使う要件があるなら、限定形式だけでは足りない可能性がある。一方、その要件がなければ、汎用的な解析を先に増やすより、受理する形式を明示し、型・生成・ブラウザまで接続して確かめる選択肢がある。

独自のGuardrailが通す形式と、フレームワークが扱える形式は別に確認する。厳格なToken制約と、その表現に固有の任意値指定が両立するかも、採用バージョンの型と生成結果で確かめる。例外を認めるために制約全体を緩める必要があるとは限らない。

## 生成処理は判断の複製になっていないか

生成する前に、入力と成果物のそれぞれに何の情報があるかを確認する。既存定義から求められる一覧を生成処理へ手書きすると、定義と生成処理を別々に修正する必要が生まれる。

フォントなら、利用するフォント・太さ、アセット提供元との対応、必要なCSS、ブラウザへの配信を分けて考える。既存のText Styleから利用の組を導けるなら、生成処理はその導出と解決を担当できる。アセット提供元が既に持つ`@font-face`やバイナリまで再生成する必要があるかは別に問う。

選択肢は、手動指定と整合検査、既存定義からの生成、フレームワークの既存機能等になる。生成を選ぶ理由は「自動化できる」ことだけでなく、独立した判断の重複を減らせるかで評価する。入力の変更への追従、欠落の検出、重複除去、空の生成先からの再現を確認し、生成成功と配信成功は別に検証する。

生成時に定義を読む関係と、配信パッケージが実行時に依存する関係も分ける。詳しい比較は[フォントの事例](case-studies/font-ownership.md)を参照する。

## 互換性を制約にする前に、対象を確認する

公開済みAPIや利用者がいる場合、互換性は実際の制約になる。破壊的変更の影響と、移行の方法・期間を評価する必要がある。

一方、未公開・未運用のAPIでは、既存配置やimport先を守ることだけを設計理由にしない。今から配置できるならどこが自然かと、変更作業量がどれだけあるかを分けて比較する。古いエントリーポイントのaliasを残すなら、誰の何を守るのかを説明できるか確認する。

[フォントの配置の再評価](case-studies/font-ownership.md#配置を維持する理由から責務を分ける理由へ)はこの前提の訂正だった。公開済みAPIの互換性を軽視する教訓ではない。

## レスポンシブでは、意味と構成を分ける

最初に、変更すべきなのが意味・情報量・配置のどれかを確認する。条件のない既定値を端末名と同一視せず、その構成がどの空間で成立するかを見る。

| 問い                         | 確認する選択肢・条件                                                                                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 幅はどこで決まるか           | 文書全体の構成ならビューポートが関係する。埋め込み先や入れ子で幅が変わるなら、利用可能領域を測るContainer Queryが判断対象と合うか検討する              |
| 条件を共有してよいか         | 同じ値を使う便利さだけでなく、各Component・Patternの成立条件を確認する。境界の直前・一致・直後と、長い内容・文字拡大も見る                             |
| 狭い領域へどう収めるか       | 文字や操作領域の縮小を前提にせず、DOM順と意味を保つ縦並び、折り返し、内部スクロール等を比較する                                                        |
| overflowはどこで起きているか | ページ全体だけでなく、Componentの内容領域・padding・文字範囲を確認する。既存の組み合わせで解決できるか調べてから、共通Typographyの変更が必要か判断する |

HTML既定のmarginを消すことと、外側の余白を選ぶことも分ける。表示の都合だけで見出しのHTMLレベルを変えたり、局所的なはみ出しを理由に全Text Styleへ改行規則を加えたりしていないか確認する。[Responsive / Typographyの事例](case-studies/responsive-typography.md)は判断の一例であり、その条件値や余白選択は汎用の解ではない。

## 操作状態と利用環境を入力として扱う

状態ごとの静止画だけでなく、状態の重なりと環境変化を選んで確認する。

- **優先順位:** disabled・loadingに、通常appearanceやhover・activeが残らないか。見た目と実際の操作可否が矛盾していないか。
- **フォーカスとバリデーション:** フォーカスと入力エラーを別々に伝えられるか。どのDOMが実際にフォーカスを持つか。キーボードとポインターの違いを一律の表示規則で消していないか。
- **利用環境:** reduced motionやforced colorsでも文言・ARIA・操作が成立するか。動きを止めたときに情報まで失わないか。
- **ホストページとPortal:** CSSの読み込みだけで意図しない範囲まで変更しないか。適用範囲を限定した場合、Portalが必要な基礎設定を失わないか。
- **テキスト方向とsafe-area:** テキスト方向（LTR・RTL）を初回表示時だけの値として扱っていないか。左右非対称のsafe-areaと方向変更で、物理方向から論理方向への対応を検査できるか。
- **内部ライブラリとの接続:** ライブラリのインラインスタイルが、定義した余白・重なり順・状態を上書きしていないか。

すべての環境へ新しい管理機構を作ることが目的ではない。対応すべき環境の変化を特定し、CSSで成立する部分とDOM・操作側で接続が必要な部分を分ける。[Interaction / Environmentの事例](case-studies/interaction-environment.md)では、承認済みの責務を維持したままブラウザ検査を追加・修正した。

## 検証層ごとに、確認できることを決める

同じ利用例を複数の層へ通すと、ある層の許可例が次の層では成立しない問題を調べやすい。ただし、全層を通った一例も、すべての使い方の保証ではない。

| 検証層                       | 主に確認すること                                         | それだけでは確認できないこと                   |
| ---------------------------- | -------------------------------------------------------- | ---------------------------------------------- |
| ソースコード・文書のレビュー | 定義・実装の配置、判断の重複、依存方向、説明と実装の対応 | 実行時のCSS解釈や操作結果                      |
| 利用範囲の静的検査           | 対象ファイル・構文・入力が許可規則に従うか               | 検査対象外の経路、型・生成・ブラウザでの成立   |
| TypeScript                   | 型チェックが通るか、禁止例が型で拒否されるか             | CSSの生成内容やブラウザの解釈                  |
| 生成結果                     | 必要なCSS・型・参照先が出力されるか、再生成で再現するか  | コマンド成功だけでは出力の意味、実要素への適用 |
| 単体・契約テスト             | 限定入力の処理、公開境界、導出や拒否の条件               | 未検査の入力、実ブラウザのカスケードや環境     |
| Storybook                    | 状態や組み合わせを再現し、目視・自動検査へ渡す場         | ビルド成功だけでは見た目・操作の正しさ         |
| ブラウザ操作                 | 実DOM、computed style、フォーカス、環境変化              | 検査していないブラウザ・操作・組み合わせ       |
| axe等                        | 対象範囲で自動検出できるアクセシビリティ違反             | 意味の適切さや操作の使いやすさ全体             |
| 画像比較                     | 基準画像がある対象での視覚差分                           | 操作・ARIA・基準自体の妥当性、対象外ストーリー |
| analyze等                    | そのツール・設定で集計された利用状況                     | 集計外の機能の不成立、設計の良否               |

Native Specは定義を調べるための生成された一覧、MCPは既存定義やライブラリAPIを問い合わせる支援として扱える。詳細が足りなければ定義や実装へ戻る。これらの観測・問い合わせ結果を新しい定義元にしたり、集計数へ合わせるために定義・実装の配置を変えたりしない。

検証を選ぶ際は「何が成功したら、この問いへ答えられるか」を先に決める。型・生成・ブラウザの不一致を確認した[Visualの検証記録](evidence/visual-guardrails.md#vg-e04)と、analyzeの観測範囲を分けた[記録](evidence/visual-guardrails.md#vg-e07)が具体例になる。
