# Design Systemの設計レビューガイド

承認済みの設計へ実装が従っているかと、その設計自体が要件に合っているかを分けて評価するためのガイドです。Animicの事例から、判断と実装、観測と解釈を混同しない進め方を整理しています。現在のコード規則や検証コマンドは[実装規約](../conventions.md)・[開発手順](../../CONTRIBUTING.md)が所有します。

## 二つのレビューを混ぜない

| 種類                   | 中心となる問い                                          | 見るもの                                                                                       | 結論の範囲                                                                               |
| ---------------------- | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 適合性の確認           | 承認済みのDesign / Architectureどおりに実装されているか | 公開API・exports、禁止import、variant・状態、Guardrail、テストの確認範囲、生成物、文書との一致 | 一致、実装不備、検査不足、文書の不一致。未承認の仕様を補って修正しない                   |
| 設計そのもののレビュー | その分担・制約は、現在の要件に対して自然か              | 変更理由と所有場所、同じ判断の重複、不要な公開範囲、実際に必要な自由度、実装後に分かった負担   | 現状維持、根拠のある変更提案、未決事項。適合していることだけを設計の妥当性の証明にしない |

どちらも問題を見つけること自体を成功条件にしない。「現在の設計のままでよい」は正式な結論である。別の見出しや抽象化も可能、一般論では別構成が多い、といった理由だけでは変更を求めない。

適合性の確認中に設計の論点が出たら、仕様違反とせず別に記録する。設計レビュー中に承認済み状態との不一致が出たら、アーキテクチャ全体の欠陥とせず、まず実装上の問題かを切り分ける。

## レビューの進め方

1. **問いと範囲を定める。** 何を判断するレビューか、調査だけか、承認済み修正まで行うかを確認する。単に「改善点を探す」を目的にしない。
2. **決定済み・レビューで判断すること・未決定を分ける。** 参照する承認内容と、変更対象外の契約を明らかにする。一時的な呼称や作業指示を、恒久的な設計用語へ昇格させない。
3. **現在の定義・実装・テスト・文書を読む。** 検索は場所を探す補助とし、関係する処理と説明を通して確認する。テスト名だけでなく入力・操作・アサーションを見る。
4. **必要な過去だけ参照する。** 設計事例と検証記録から前提や失敗を知る。古いコード例を現在の許可形式として扱わず、現在の利用方法は現行資料で確認する。
5. **問題があるという前提を置かない。** 質問されたことや複雑に見えることだけでは、変更の根拠にしない。反対に、承認済みであることを追加検証不要の理由にもしない。
6. **変更しない案を含めて比較する。** 各案が満たす要件、失う自由度、変更が及ぶ場所を示す。必要なら検査だけの修正と、設計変更を伴う案を分ける。
7. **理由の出所を確認する。** 現在の要件、実際の公開利用者、既存配置への慣性、将来予測のどれかを区別する。作業量は把握しても、それだけで責務の適切さを決めない。
8. **確かめられる主張を検証する。** 最小入力を用意し、問題の層に合う検査を使う。型やGuardrailだけでなく、必要なら生成結果・ブラウザ・環境変更まで同じ利用例を通す。
9. **結果の証明範囲を記す。** 観測した入力・環境・結果と、その結果が示すこと・示さないことを明らかにする。限界を書くのは、省くと結論の強さや適用・検証範囲を誤解させる場合に限る。現在の成功を過去の成功へ、限定入力の成功を全利用方法へ広げない。
10. **判断が必要な点を実装と分けて返す。** 新しいDesign / Architecture判断は勝手に確定せず、既存判断では決まらない理由と選択肢を示す。既に承認された修正と未決部分を混ぜない。

実装後の再レビューでは、変更が目的を満たしたかに加え、公開範囲が広がっていないか、同じ判断を別の場所へ複製していないか、検証が修正後の入力を実際に扱っているかを確認する。成功したコマンド数を結論の代わりにしない。

## 事実・提案・決定・解釈を分ける

| 分類         | 記録する内容                                             | 混同しやすいもの                                     |
| ------------ | -------------------------------------------------------- | ---------------------------------------------------- |
| 観測事実     | その入力・環境・時点でコードやブラウザから確認できたこと | 現在のコードから推測した過去、成功ログに残らない詳細 |
| 当時の提案   | 実際に比較対象となった案と、その時点の利点・懸念         | 後から思い付いた案、実装していない案の性能評価       |
| 決定         | 誰の判断として何を採り、何を維持・保留したか             | 実装者が都合で選んだ値を承認済みとして扱うこと       |
| 後からの解釈 | 複数の観測・判断から整理した教訓や再利用できる問い       | 当時から明文化されていた原則、実測した一般法則       |

比較案が実装されていない場合は、保守コストや性能の優劣を測ったとは書かない。承認された判断と、実装で観測した結果も分ける。限界は結論を過剰に一般化しないために記し、調査者が確認できなかった事項の一覧を作ることを目的にしない。例えば、別々の検査を一貫したE2Eと読ませない説明は必要だが、結論の読み方に影響しない調査上の不足は記載しない。

## 見つかった問題を分類する

| 分類         | 判別する問い                                                         | 対応                                                                                            |
| ------------ | -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 実装不備     | 承認済みの振る舞いは明確で、実装だけが一致していないか               | 契約を変えない最小修正と再発検査を示す。disabledの状態競合がこの例                              |
| 検査不足     | テストが必要な入力・状態・層を実際に確認しているか                   | 欠けた検査を示す。文字列のGuardrail fixtureが型検査されない問題など、テスト成功の範囲を訂正する |
| 設計上の問題 | 実装は従っていても、責務の重複や不要な制約が具体的な要件と衝突するか | 現状維持と変更案の両方について、所有場所・利用方法・検証の変化を示す                            |
| 未決定事項   | 既存判断だけで採否・意味・適用範囲を決められるか                     | 決められない箇所で実装を止め、判断に必要な材料を返す                                            |

一つの発見が複数の分類を含むこともある。Visualの検査漏れは実装の問題であっても、どのJavaScript形式を許可するかは設計判断を含んだ。分類名を付けるだけで終わらず、何が確定済みで何が未決かを説明する。

## ツール結果を、目的の成立と同一視しない

検証層ごとの確認範囲は[設計ガイドの表](design-guide.md#検証層ごとに確認できることを決める)を使う。レビューでは、報告された成功がその問いへの証拠になっているかを次の順で読む。

1. **入力を見る。** 実際の利用例か、文字列のfixtureか、別の個別検証か。任意クラスのGuardrailとブラウザ確認のように入力経路が別なら、一貫したE2Eとは呼ばない。
2. **成功条件を見る。** Guardrailは検査した構文、TypeScriptは型の成立を示す。生成コマンドが成功しても、必要なCSS構造があるかは別に確認する。
3. **ブラウザで何をしたかを見る。** 計算済みスタイル、CSSOM、実要素のアニメーション、キーボード操作は別の確認である。初回表示だけか、disabled中のhoverやmount後の方向変更まで扱ったかを確かめる。
4. **比較対象を見る。** 画像比較の成功は基準画像の対象に限る。操作や意味、基準画像自体のデザイン上の妥当性まで承認したことにはならない。
5. **集計範囲を見る。** analyzeの数値はそのツール・設定での観測である。0の原因を確認できなければ未確定とし、生成物やブラウザでの成立を別に調べる。数値を増やすために設計を合わせない。

例えば[Keyframesの記録](evidence/visual-guardrails.md#vg-e04)は、生成コマンドが成功しても有効なフレームを得られなかった。別の[analyzeの記録](evidence/visual-guardrails.md#vg-e07)では0という集計とブラウザでの成立が併存した。両者ともツール全般が不正確だという結論ではなく、目的と観測範囲を分ける材料になる。

## AIを使う場合の偏りを管理する

AIへの依頼文にも、レビューの問い、確定事項、変更しない範囲と、変更不要が有効な結論であることを含める。次は事例から得た確認観点であり、すべての偏りが実測されたという一覧ではない。

| 偏り                 | 確認する問いと対処                                                                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 既存配置への慣性     | 「すでにここにある」「変更量が少ない」を責務の理由にしていないか。必要なら置き直せる前提で比較し、変更量は別の情報として扱う         |
| 存在しない互換性制約 | 実際に公開・運用されたAPIと利用者がいるか。[書体の事例](case-studies/font-ownership.md)の前提訂正と、公開済みAPIの移行問題を区別する |
| ツール中心の判断     | lint・型・生成成功やanalyzeの数値が、何を証明するかを説明させる。目的を満たす入力と観測へ戻す                                        |
| 過剰な一般化         | 一つの事例の許可形式・パッケージ構成・幅条件を他案件へ持ち込んでいないか。適用条件と成立しない可能性を併記する                       |
| 抽象化の先回り       | 汎用解析、共通Component、共通Tokenを必要とする具体例があるか。将来の自由度だけで増やさず、限定した形式と現状維持も比較する           |
| 問題発見への誘導     | 「問題を探せ」という依頼を、問題の存在証明にしていないか。指摘には不一致・重複・迂回経路・未検査の成立条件など具体的根拠を求める     |
| 実装と判断の混同     | 承認済みの不備修正か、新しい意味・公開範囲の選択か。後者を実装で既成事実にせず、人の判断へ戻す                                       |

AIは調査、比較案の整理、検証の接続に使える。一方、未承認のToken・API・条件・責務を、実装を進めるためだけに埋める役割にはしない。問いの偏りへの対処は、現状維持を自動的に優先することでもない。

## 変更案と判断依頼を具体化する

変更を提案する場合は、現状の問題と根拠に加え、どの定義・生成・フレームワーク実装・利用箇所・テスト・文書へ変更が及ぶかを示す。不要な中間層を増やす抽象案だけでは、改善になるか比較できない。

新しい判断を返すときは、次を揃える。

- 現在の承認内容と、レビューで確認した事実。
- 既存判断だけでは決められない点。実装不備や単なる記録不足との違い。
- 現状維持を含む選択肢、各案の適用条件・影響・未検証部分。
- 推奨案とその根拠。将来予測を使う場合はその前提。
- 判断後の最小変更と、成立を確かめる検証。

確定した判断の範囲だけを実装し、検証後は「変更したもの」と「変更しなかったもの」を確認する。問題がなければ変更不要と報告する。結論に必要な検証が未実施なら、その入力・状態・環境と判断への影響を示し、全体を未達または成功と一括りにしない。
