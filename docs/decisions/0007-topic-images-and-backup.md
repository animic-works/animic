# 0007: お題の画像をR2に保存し、管理画面のデータをZIPで書き出す

- 状態: 承認済み
- 決定日: 2026-10-08
- 関連: [ゲーム仕様](../product.md#お題の管理)、[アーキテクチャ](../architecture.md#管理画面)、[ADR 0005](0005-operator-password.md)、Issue #28

## 背景

お題はD1の`topic`へSQLで登録しており、画像は別の場所に置いたURLを登録する必要があった。管理画面からお題・対戦条件の候補・よく使う表現を登録できるようにすると、画像の置き場所と、NovelAIの画像に残るメタデータの扱いを決める必要がある。NovelAIで保存したPNGには、生成に使ったプロンプト（お題の答え）がテキストとして埋め込まれている。

画面で登録したデータは、D1・R2の障害や操作ミスで消えると戻せない。D1のTime Travelで戻せるのは7日前（Workers Free）または30日前（Workers Paid）までで、R2の画像は対象外である。ローカルと本番の間でデータを移す手段もない。

## 判断基準

- 運営者が画面だけで画像を登録でき、配信先を別に用意しなくてよいこと。
- 参加者へ配信する画像に、お題の答えが残らないこと。
- Workers Freeの制限（1リクエストあたりCPU時間10ms、メモリ128MB、D1は1回の呼び出しで50クエリ）に収まること。
- 画像を含めて、別の環境へ戻せること。

## 検討した選択肢

### 画像の置き場所

| 選択肢               | 利点                                     | 欠点・制約                                       |
| -------------------- | ---------------------------------------- | ------------------------------------------------ |
| R2へアップロードする | 画面だけで登録でき、Workerから直接読める | R2のバケットを追加し、本番で作成する手順が増える |
| 画像のURLを入力する  | 今のSQLの登録と同じで、追加の構成がない  | 配信先を別に用意し、運営者が置き場所を管理する   |
| D1に画像を保存する   | 構成が1つで済む                          | 行の大きさの上限があり、配信のたびにD1を読む     |

### メタデータを消す場所

| 選択肢                             | 利点                                                | 欠点・制約                                                |
| ---------------------------------- | --------------------------------------------------- | --------------------------------------------------------- |
| ブラウザーのcanvasでWebPに描き直す | 追加の料金・設定がない。サーバーのCPU時間を使わない | WebPを書き出せないブラウザーでは登録できない              |
| Images bindingでサーバーが変換する | ブラウザーに依存しない                              | 料金と設定が増える                                        |
| Workerでチャンクを読んで取り除く   | 追加の構成がない                                    | 形式ごとの処理が要り、CPU時間10msに収まらないおそれがある |

### 書き出しの形式

| 選択肢                              | 利点                                           | 欠点・制約                                         |
| ----------------------------------- | ---------------------------------------------- | -------------------------------------------------- |
| ZIP（JSONと画像）をブラウザーで作る | R2が消えても戻せる。サーバーの制限に依存しない | 画像の数だけブラウザーのメモリを使う               |
| JSONだけを書き出す                  | 小さく単純                                     | 画像はR2に残っている前提になり、R2の障害で戻せない |
| ZIPをWorkerで作る                   | ブラウザーに依存しない                         | CPU時間とメモリの上限に収まらない                  |

## 決定

- お題の画像はR2のバケット（binding `TOPIC_IMAGES`、バケット`animic-topic-images`）の`topics/<お題ID>/<画像ID>`に保存し、`/topic-images/<お題ID>/<画像ID>`で配信する。画像IDは差し替えのたびに変え、配信は長くキャッシュさせる。古い画像は消さない。
- 管理画面は、選んだ画像をcanvasに白で塗ってから描き直し、WebPにして送る。サーバーはWebPの形式を確かめ、EXIF・XMPのチャンクやアニメーションがあれば拒否する。
- 書き出しは、`backup.json`（`animic-backup/1`）と画像を1つのZIPにする。ZIPの作成と展開はブラウザーで行う。読み込みは同じIDを上書き・ないものを追加し、削除はしない。書き込みは20件ずつに分けてServer Functionへ送る。
- 対象はお題・対戦条件の候補・よく使う表現とし、採点ワーカー（秘密情報を含む）・採点ジョブ・対戦結果・参加者の情報・生成画像は含めない。

## 理由

R2はWorkerから直接読め、運営者が配信先を用意しなくてよい。D1は画像の保存に向かない。canvasで描き直すと、PNGのテキスト・EXIF・XMPなどの形式を問わずメタデータと透過が消え、サーバーの処理はチャンクの確認だけで済む。サーバーでの変換は、料金かCPU時間の制約がある。ZIPに画像を含めると、D1とR2の両方が消えても戻せる。Workerで作るとCPU時間とメモリの上限を超えるため、ブラウザーで作る。

## 影響

- 本番では、デプロイ前にR2のバケットを作成する必要がある。
- 管理画面でお題を登録・差し替えするには、WebPを書き出せるブラウザー（Chromeなど）が要る。
- 削除・差し替えで使わなくなった画像はR2に残る。整理の手段はない。
- 画像のURLを知っていれば、非公開のお題の画像も取得できる（URLはUUIDのため推測できない）。
- 採点ワーカーへ渡すお題の画像は、自分のURLへ通信せずR2から読む。
- 読み込みが途中で失敗した場合は、同じZIPを読み込み直す。

## 見直す条件

お題の数が増えてブラウザーでZIPを扱えなくなった場合、Workers Paidへ移ってサーバーで変換・圧縮できるようになった場合、R2に残る古い画像の量が問題になった場合に再検討する。

## 根拠

2026-10-07〜08に、Cloudflareの資料（[D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)、[D1の制限](https://developers.cloudflare.com/d1/platform/limits/)、[Workersの制限](https://developers.cloudflare.com/workers/platform/limits/)、[R2の料金](https://developers.cloudflare.com/r2/pricing/)）と、[WebPのコンテナの仕様](https://developers.google.com/speed/webp/docs/riff_container)を確認した。ZIPには`fflate` 0.8.3を使う。
