# 0006: 参加者のログインをGoogle・DiscordのOAuthで提供する

- 状態: 承認済み
- 決定日: 2026-10-07
- 関連: [ゲーム仕様](../product.md#ログイン)、[アーキテクチャ](../architecture.md#参加者のログイン)、[ADR 0003](0003-anonymous-sessions.md)

## 背景

参加者はBetter Authの匿名セッションで識別している（[ADR 0003](0003-anonymous-sessions.md)）。匿名セッションはブラウザのCookieにだけ結び付くため、Cookieを消したり別の端末を使ったりすると、同じ参加者として扱えない。ADR 0003は、アカウント連携と別端末への復帰を見直す条件にしている。

ルームを作る人にはログインを求め、ルームURLから参加する人はログインしなくても遊べるようにする。

## 判断基準

- 匿名参加と同じ仕組み（Better Auth・D1のセッション・WebSocketの失効確認）の上で動くこと。
- 参加者にパスワードやメールの確認を求めないこと。
- 友だちと遊ぶ参加者が持っている見込みの高いサービスであること。
- 実際のOAuthを使わずに、ログインした状態をE2Eで確かめられること。

## 検討した選択肢

| 選択肢                                     | 利点                                                                          | 欠点・制約                                                       |
| ------------------------------------------ | ----------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Better Authの`socialProviders`             | 追加のパッケージが不要。匿名ユーザーからの切り替えをanonymousプラグインが扱う | サービスごとにOAuthアプリと秘密情報を管理する                    |
| メールアドレスとパスワード・マジックリンク | 外部サービスのアカウントが要らない                                            | パスワードの保管やメール送信の仕組みが増え、参加者の手間も増える |

サービスは、GoogleとDiscordにする。XはAPIが有料のため使わない。GitHubは、メールアドレスを非公開にでき取得に失敗することがあるなど、認証の手間に対して参加者が使う見込みが小さいため使わない。

## 決定

- Better Authの`socialProviders`で、GoogleとDiscordのログインを提供する。OAuthクライアントのIDと秘密情報の両方を設定したサービスだけを有効にする。
- ルームを作るときはログインを必須にする。ルームURLから参加する人のログインは任意とし、ホストの引き継ぎ先はログインの有無で区別しない。
- 参加者IDは、Better AuthのユーザーIDのままとする。同じアカウントでログインすれば、別の端末・ブラウザでも同じ参加者になる。
- 匿名の参加者がログインしたら、匿名ユーザーは削除せず、そのセッションをすべて失効させる。匿名で参加したルームの参加記録は引き継がない。
- 同じメールアドレスのアカウントの連携は、Better Authの既定に従う。サービスが確認済みのメールアドレスを返し、既存のユーザーのメールアドレスも確認済みの場合だけ連携する。
- E2Eでは、`ANIMIC_E2E=true`のビルドにだけ含めるBetter Authのプラグインで、ログインした状態を作る。

## 理由

`socialProviders`は匿名参加と同じD1のセッションを発行するため、WebSocketの期限・失効の確認やCookieの保護をそのまま使える。メールアドレスとパスワードは、参加者の手間と運営の管理を増やす。

ルームを作る人をアカウントで識別でき、匿名のままルームを作り続けることを防げる。参加者は、招待されたURLからログインせずにすぐ遊べる。ホストの引き継ぎ先をログインした参加者に限ると、ログインした参加者がいないときにホストが不在になり、対戦を始められなくなる。ルームのDOに参加者ごとのログイン状態を持つ必要も出る。

匿名のセッションを残すと、同じブラウザのほかのタブが匿名の参加者IDでルームに接続したまま、そのタブからの操作はログイン後の参加者IDで送られて食い違う。セッションを失効させれば、既存の失効の確認でその接続を閉じられる。ルームの中の参加者IDを書き換えると、進行中の対戦の提出や権限の判定が複雑になるため、参加記録は引き継がない。

## 影響

- 開発用と本番用のOAuthアプリと、Workerの秘密情報（`GOOGLE_CLIENT_ID`・`GOOGLE_CLIENT_SECRET`・`DISCORD_CLIENT_ID`・`DISCORD_CLIENT_SECRET`）の管理が必要になる。
- ログイン時に、メールアドレス（確認済みかどうかを含む）・アカウントの名前・プロフィール画像のURL・サービス上のユーザーID・サービスのトークンをD1に保存する。利用規約とプライバシーポリシーへの記載が必要になる。
- 匿名で遊んでいた参加者がログインすると、同じブラウザで開いているルームの接続は閉じる。そのルームには新しい参加者として入り直す。
- 同じメールアドレスでも、確認状態によっては別のサービスでログインできない（`account_not_linked`）。

## 見直す条件

匿名で参加したルームへの復帰や記録の引き継ぎが必要になった場合、GoogleとDiscord以外のサービスが必要になった場合、運営者の判定に参加者のアカウントを使う場合に再検討する。
