# 0011: 生成画像を専用のR2バケットに保存し、URLを知っていれば取得できる形で配信する

- 状態: 承認済み
- 決定日: 2026-10-08
- 関連: [ゲーム仕様](../product.md#画像生成)、[アーキテクチャ](../architecture.md#依存関係とクライアントサーバーの分離)、[採点の設計](../scoring.md)、[ADR 0007](0007-topic-images-and-backup.md)、[ADR 0008](0008-generated-image-webp.md)、Issue #12、Issue #35

## 背景

参加者が対戦で生成した画像は、本人の履歴に表示し、提出した1枚を採点ワーカーへ渡し、結果の確定後は相手にも見せる。生成キューのDOはメタデータと透過のないWebP（約0.13MB）を返す（ADR 0008）が、それを保存する場所と配信の方法がなかった。

生成画像は対戦のたびに増え続ける。運営者が管理画面で登録するお題の画像（ADR 0007）は、失うと戻せないためZIPで書き出しているが、生成画像は書き出しの対象にしない。対戦の状態はルームのDOのSQLiteに1つのJSONで保存しており、画像そのものを入れる場所ではない。

## 判断基準

- Workerから直接読み書きでき、採点ワーカーへ渡すときに自分のURLへ通信しなくてよいこと。
- 結果の確定前に、相手が生成画像を見られないこと。
- お題の画像と取り違えて消したり書き出したりしないこと。後で古い生成画像を整理できること。
- 追加の料金がなく、ローカルとE2Eでも本番と同じ動きになること。

## 検討した選択肢

### 保存先

| 選択肢                                 | 利点                                                     | 欠点・制約                                                                   |
| -------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 生成画像専用のR2バケット               | お題の画像と分けて一覧・整理できる。Workerから直接読める | 本番で作るバケットが1つ増える                                                |
| お題と同じR2バケット（`TOPIC_IMAGES`） | バケットが増えない                                       | 運営者が登録した資産と参加者の生成物が混ざり、整理するときにお題を消すおそれ |
| ルームのDOのストレージ                 | 対戦の状態と同じ場所で、ルームと一緒に扱える             | 配信のたびにルームのDOを起こす。ルームを閉じた後の配信にもDOが要る           |
| D1                                     | 構成が増えない                                           | 行の大きさに上限があり、配信のたびにD1を読む                                 |

### 配信

| 選択肢                                                    | 利点                                                           | 欠点・制約                                                              |
| --------------------------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Server Routeで配信し、セッションを確かめない              | お題の画像と同じ仕組みで、`img`と採点ワーカーへURLのまま渡せる | URLが漏れると誰でも見られる                                             |
| 配信のたびにセッションと対戦の参加者を確かめる            | URLが漏れても本人以外は見られない                              | 結果の確定後に相手へ見せるため、配信のたびにルームのDOの状態を読む      |
| R2の公開バケット（r2.devまたはCustom Domain）から配信する | Workerを通らない                                               | 本番とローカル・E2Eで配信先が変わる。公開の設定とドメインの管理が増える |

## 決定

- 生成画像は専用のR2バケット（binding `GENERATED_IMAGES`、バケット`animic-generated-images`）の`generations/<対戦ID>/<処理ID>`に、生成キューのDOが返したWebPのまま保存する。キーに対戦IDを含め、別の対戦で同じ処理IDが使われても上書きしない。
- `/generated-images/<対戦ID>/<処理ID>`のServer Routeで配信する。セッションは確かめず、`Cache-Control: private, max-age=31536000, immutable`を付ける。存在しない画像は`no-store`の404にする。
- 対戦の状態には`BETTER_AUTH_URL`を基にした絶対URLを記録し、本人への状態配信と採点ジョブの入力に使う。
- 採点ワーカーへ渡すときは、自分のオリジンの`/generated-images/`のURLをR2から直接読む。
- 管理画面のバックアップ（ZIP）には含めない。古い生成画像は消さない。

## 理由

R2はWorkerから直接読み書きでき、配信の料金がかからない。お題の画像とバケットを分けると、運営者の資産と対戦ごとに増える生成物を取り違えずに一覧・整理でき、後で生成画像だけを消す設定もできる。DOとD1は画像の保存に向かない。

処理IDはUUIDで、結果の確定前は本人にだけ配信する（相手の生成履歴は状態配信に含めない）ため、確定前に相手がURLを知る手段はない。そのため配信のたびに認可しなくても、確定前の画像は本人以外に見られない。配信のたびにルームのDOを読むと、画像1枚ごとにDOを起こすことになり、確定後の公開や共有とも両立しにくい。同じURLの画像は変わらないため長くキャッシュさせ、本人向けの画像を共有のキャッシュに置かないよう`private`にする。Workerから自分の公開URLへ通信すると、workers.devでは失敗し、Custom Domainでは自分のWorkerをもう一度通るため、採点ワーカーへ渡す画像はR2から読む。

## 影響

- 本番では、デプロイ前に`animic-generated-images`のバケットを作成する必要がある。
- 生成画像はR2に残り続ける。古い画像を整理する手段はまだない。
- URLを知っていれば、誰でも生成画像を取得できる。URLを共有すると、本人以外も見られる。
- `scoring`が`image-generation`の`generated-images.server.ts`に依存する。

## 見直す条件

生成画像の量がR2の無料枠（月10GB）に近づいた場合、結果をSNSで共有する画面で公開の範囲を決める場合、生成画像の配信に認可が必要になった場合に再検討する。

## 根拠

2026-10-09に、Cloudflareの資料（[R2の料金](https://developers.cloudflare.com/r2/pricing/)、[Workersの`waitUntil`](https://developers.cloudflare.com/workers/runtime-apis/context/)）を確認した。R2の無料枠は保存が月10GB、書き込み（Class A）が月100万回で、R2からの配信に転送料金はかからない。生成画像1枚を約0.13MB（ADR 0008）とすると、無料枠の保存は約7万枚に当たる。E2Eでは、ローカルのR2に保存した画像の配信と、採点ワーカーへの受け渡しを確かめた。
