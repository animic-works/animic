# 0005: 運営者の管理画面を共通のパスワードで保護する

- 状態: 承認済み
- 決定日: 2026-10-04
- 関連: [アーキテクチャ](../architecture.md#運営者の認証)、[採点の設計](../scoring.md)

## 背景

採点ワーカーを登録するリンクコードの発行や、採点ワーカーの失効は、運営者だけが行える必要がある。Issue #7では、運営のGitHubアカウントでログインし、GitHubのユーザーIDを許可リストと照合する案を検討していた。その後、AnimicではGitHubでのログインを、運営者・参加者のどちらにも使わないことにした。

## 検討した選択肢

| 選択肢                           | 利点                                                  | 欠点・制約                                                                                                        |
| -------------------------------- | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| GitHubログインと許可リスト       | 運営者ごとに識別でき、パスワードを共有しない          | 開発用・本番用のGitHub OAuth Appが要る。参加者の匿名セッションと同じBetter Authに組み込むため、確認の手間が大きい |
| 共通のパスワードと署名付きCookie | 秘密情報を1つ設定するだけで使える。参加者の認証と独立 | 運営者を個別に識別できない。パスワードが漏れたら変更が要る                                                        |

## 決定

Workerの秘密情報`ADMIN_PASSWORD`と一致するパスワードでログインした場合だけ、管理画面（`/admin`）と管理用のServer Functionsを使えるようにする。ログイン後は、12時間有効な署名付きのCookieで判定する。

## 理由

GitHubでのログインはAnimicで使わないため、GitHubログインと許可リストの案は採らない。運営者は少人数で、操作はリンクコードの発行・採点ワーカーの失効・状態の確認に限られる。共通のパスワードなら秘密情報を1つ設定するだけで済み、参加者のセッションにも影響しない。

## 影響

- パスワードは12文字以上にし、ローカルと本番で別の値にする。パスワードを変えると、発行済みのCookieも使えなくなる。
- 誤ったパスワードへの応答を1秒遅らせるが、試行の回数制限はない。
- サーバー側にセッションを保存しない。ログアウトはブラウザのCookieを削除するだけなので、期限内のCookieを無効にするにはパスワードを変える。
- 誰が操作したかは記録しない。

## 見直す条件

運営者が増えて個別の権限や操作の記録が必要になった場合、またはパスワードの総当たりを観測した場合に再検討する。
