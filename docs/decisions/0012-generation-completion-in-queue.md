# 0012: 生成キューのDOが生成画像の保存とルームのDOへの完了の通知まで行う

- 状態: 承認済み
- 決定日: 2026-10-12
- 関連: [アーキテクチャ](../architecture.md#画像生成と配信)、[ADR 0008](0008-generated-image-webp.md)、[ADR 0011](0011-generated-image-storage.md)、Issue #84

## 背景

生成は、`generateImage`のServer FunctionがルームのDOで受け付け、生成キューのDOの`generate`からWebPを受け取り、R2に保存してルームのDOの`finishGeneration`に結果を渡していた。参加者が通信を切っても続けるため、この処理を`waitUntil`に登録していた。

`waitUntil`は応答の送信か通信の切断から30秒までしか続かない。生成はNovelAIの順番待ちを含めて最大1分かかるため、「生成する」の直後に再読み込みすると、NovelAIで生成できても保存と完了の通知の前に止まることがあった。その生成は1分後にタイムアウトで失敗になり、生成した画像は使われない。

また、`compatibility_date`（2026-09-21）では、呼び出し元の通信が切れた後に、処理中のI/OがDOをメモリに留めない。

## 判断基準

- 参加者の通信が切れても、受け付けた生成を完了まで進めること。
- Workers Freeで、DOの実行時間などの使用量を増やさないこと。
- 依存の向きを増やしすぎないこと。

## 検討した選択肢

| 選択肢                                                 | 利点                                                                   | 欠点・制約                                                                    |
| ------------------------------------------------------ | ---------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 生成キューのDOがR2への保存と`finishGeneration`まで行う | 生成の間ずっと動いている生成キューのDOで完結し、実行時間がほぼ増えない | 生成キューのDOがルームのDOを呼ぶ。依存の向きが1本増える                       |
| ルームのDOが生成キューのDOを呼び、完了まで待つ         | 生成の呼び出し側が採点と同じルームのDOになる                           | ルームのDOが生成の間（最大1分）休止できず、生成のたびに実行時間の課金が増える |
| 今のまま`waitUntil`で待つ                              | 変更がない                                                             | 切断から30秒で止まる生成が残る                                                |
| Queuesなどへ完了の処理を移す                           | 呼び出し元から完全に切り離せる                                         | 構成が増える                                                                  |

## 決定

- 生成キューのDOの`generate`は、ルームのコード・対戦ID・処理IDを受け取り、生成・WebPへの変換・R2への保存・ルームのDOの`finishGeneration`までを行う。`generateImage`はルームのDOで受け付けた後、`generate`を待つだけにする。
- 生成キューのDOから呼ぶのは、ルームのDOの`finishGeneration`だけにする。採点の処理からはルームのDOを呼ばない。
- 互換性フラグ`durable_object_io_tasks_prevent_eviction`を有効にし、呼び出し元の通信が切れても、処理中のI/OがあるDOをメモリに留める（最長15分）。

## 理由

生成キューのDOは生成の間ずっと動いているため、R2への保存と完了の通知を加えても実行時間はほぼ変わらない。ルームのDOに待たせると、WebSocketの休止で抑えていた実行時間が生成のたびに増え、Workers Freeの枠を使う。Queuesは確実だが、今の規模では構成を増やすほどの理由がない。

## 影響

- 参加者が通信を切っても、生成は完了まで進み、結果は状態配信で届く。
- 生成キューのDOがルームのDOに依存する。ルームのDOは生成キューのDOを呼ばないため、呼び出しは循環しない。
- 互換性フラグはWorker全体に効くため、ほかのDOも、呼び出し元の通信が切れた後に処理中のI/Oが終わるまで留まる。2026-10-01以降の`compatibility_date`では既定の動きになる。

## 見直す条件

生成を待つ人数が増え、生成キューのDOが1つでは足りなくなった場合や、生成の完了を確実に届ける必要が出た場合（Queuesへの移行）に再検討する。

## 根拠

2026-10-12に、Cloudflareの資料（[Workersの`waitUntil`](https://developers.cloudflare.com/workers/runtime-apis/context/)、[互換性フラグ](https://developers.cloudflare.com/workers/configuration/compatibility-flags/)、[DOのライフサイクル](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)）を確認した。`waitUntil`は応答の送信か通信の切断から30秒まで、`durable_object_io_tasks_prevent_eviction`は2026-10-01から既定で、処理中のI/OがDOを留めるのは開始から最長15分。ローカルのworkerd（1.20261001.1）がこのフラグを知っていることを確かめた。
