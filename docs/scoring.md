# 採点の設計

## 目的と対象範囲

両者が提出した対戦で、お題に対する提出画像の再現度を採点し、勝敗を確定する仕組みを扱います。勝敗のルールは[ゲーム仕様](product.md#対戦の流れ)、全体の構成は[アーキテクチャ](architecture.md#採点)に従います。採点の実行先とキューの方式を選んだ理由は[ADR 0004](decisions/0004-scoring-workers.md)、採点ワーカーの準備と登録の手順は[CONTRIBUTING.md](../CONTRIBUTING.md#採点ワーカーの準備)を参照してください。

## 用語

| 用語             | 意味                                                                                                                                                     |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 採点ワーカー     | 運営者のPCで動く[desktop-comfyui-server](https://github.com/mintani/desktop-comfyui-server)。Animicへ採点ジョブを取りに来て、ComfyUIで採点した結果を返す |
| 採点ジョブ       | 採点の依頼1件。順番付きの入力画像と、使うワークフローの版を持つ                                                                                          |
| 採点結果         | 採点ジョブから得た参加者ごとの`total`                                                                                                                    |
| リンクコード     | 採点ワーカーを登録するための、10分間有効で1回だけ使えるコード                                                                                            |
| ワークフロー定義 | ワークフローの版ごとに、入力からワークフローJSONを組み立てる処理と、出力を参加者ごとの`total`に読み替える処理                                            |

## 役割と構成

| 配置                                             | 役割                                                                          |
| ------------------------------------------------ | ----------------------------------------------------------------------------- |
| `src/features/scoring/scoring-workers.server.ts` | 採点ワーカー向けAPI。desktop-comfyui-serverの通信仕様との変換、秘密情報の照合 |
| `src/features/scoring/scoring-jobs.server.ts`    | 採点ジョブの登録・割り当て・完了・差し戻しと、ルームのDO向けの状態取得        |
| `src/features/scoring/scoring-workflows.ts`      | ワークフロー定義。今は`illust-similarity-v1`だけを持つ                        |
| `src/features/battle/battle-state.ts`            | 採点エントリーの追加、採点結果による勝敗の確定、配信・保存する内容            |
| `src/features/room/room.server.ts`               | 採点待ちの間、Alarmで採点ジョブを登録し、状態と結果を取得して対戦へ反映する   |
| `src/server.ts`                                  | 採点ワーカー向けAPIを、TanStack Startより前に`scoring`へ振り分ける            |

desktop-comfyui-serverの通信仕様で決まっているURLパスとキー名は、`scoring-workers.server.ts`だけに書きます。`scoring`はルームのDOを呼び出さず、DOが`scoring`のサーバー処理を呼び出して結果を受け取ります。

## データと状態

### D1

テーブル定義は`src/features/scoring/scoring.schema.ts`にあります。

| テーブル            | 内容                                                                                                       |
| ------------------- | ---------------------------------------------------------------------------------------------------------- |
| `scoring_worker`    | 採点ワーカーのID・表示名・秘密情報のSHA-256・最後にheartbeatを受け取った日時と状態・失効日時               |
| `scoring_link_code` | リンクコード・登録する採点ワーカーの表示名・失効日時                                                       |
| `scoring_job`       | 対戦ID・ルームコード・ワークフローの版・入力・状態・試行回数・割り当て先・割り当ての期限・出力・失敗の理由 |
| `scoring_result`    | 採点ジョブと参加者ごとの`total`                                                                            |

採点ジョブのIDは対戦の状態で発行し、登録は冪等にします。採点ワーカーから受け取った出力は加工せず`raw_result`に保存し、そこから読み取った`total`を`scoring_result`に保存します。

採点ジョブの状態は次のように変わります。

| 状態        | 次の状態                                                                                                                |
| ----------- | ----------------------------------------------------------------------------------------------------------------------- |
| `queued`    | 採点ワーカーの要求で`running`。試行回数を1増やし、割り当ての期限を2分後にする                                           |
| `running`   | 完了の報告で出力から`total`を読めれば`succeeded`                                                                        |
| `running`   | 失敗の報告・割り当ての期限切れ・`total`を読めない出力・画像の取得失敗のとき、試行回数が2未満なら`queued`、2なら`failed` |
| `succeeded` | 変わらない                                                                                                              |
| `failed`    | 変わらない                                                                                                              |

### 対戦の状態

ルームのDOが保存する対戦の状態に、`scoring`（採点期限と参加者ごとの採点エントリー）を持たせます。採点エントリーは提出時に`pending`で追加し、採点ジョブの結果に応じて`succeeded`（`total`付き）か`failed`にします。

結果には、採点による勝ち（`higher-score`）・引き分け（`same-score`）・採点失敗による勝負不成立（`scoring-failed`）を加えます。

- 結果が確定した後は、採点ジョブの結果で対戦の状態を変更しません。
- 対戦の状態にない採点ジョブの結果は反映しません。
- 採点による結果が確定するまで、相手の`total`と提出画像を配信しません。確定後は全員の`total`と提出画像を配信し、`battle_result`へ保存するJSONにも全員の`total`を含めます。

## 処理の流れ

1. 参加者が画像を提出すると、`battle`がその提出の採点エントリーを追加し、採点ジョブのIDを発行します。
2. ルームのDOは、採点を待つエントリーがある間、3秒間隔のAlarmで採点ジョブをD1へ登録し、状態と結果を取得して対戦へ反映します。D1との通信に失敗したら、次のAlarmで再試行します。操作が続いても確認を先へ延ばしません。
3. 採点ワーカーがジョブを要求すると、期限切れのジョブを差し戻したうえで、待機中で最も古いジョブを1台だけに割り当てます。入力の順に画像を取得してbase64で渡し、ワークフロー定義で組み立てたワークフローを添えます。画像を取得できなければ、その試行を失敗として扱い、ジョブを渡しません。
4. 採点ワーカーが完了を報告すると、出力を保存し、ワークフロー定義で参加者ごとの`total`を読み取ります。
5. 全参加者の提出状態が確定し、提出者が2人以上で、全員の採点が成功したら、`total`を比べて結果を確定します。制限時間の前に全員が提出した場合も、採点がそろった時点で確定します。
6. 採点に失敗したエントリーがあるか、全参加者の提出が確定してから5分以内に採点がそろわなければ、勝負不成立とします。
7. 確定した結果は、既存の仕組みでD1の`battle_result`へ保存します。

採点ワーカーの秘密情報は、リンク時に一度だけ返し、D1にはSHA-256だけを保存します。以降の要求はBearerで受け取り、定数時間で照合します。失効日時がある採点ワーカーの要求は拒否します。

## 依存関係

- desktop-comfyui-server 0.4.0の通信仕様: 採点ワーカーがジョブを取りに来る方式、画像のbase64での受け渡し、JSONを返すheartbeat、ジョブがないときの204。
- comfyui-illust-similarityの`IllustSimilarityAll`ノード: `similarity`という出力ノードが、6指標と`total`をJSON文字列で出力します。平坦な画像でも厳密なJSONを出力する版を使います。
- D1: 採点ジョブ・採点ワーカー・リンクコード・採点結果の保存。

## 制約と検証

| 項目                           | 値   |
| ------------------------------ | ---- |
| 割り当ての期限                 | 2分  |
| 採点ジョブの試行回数           | 2回  |
| 採点期限（全員の提出確定から） | 5分  |
| ルームのDOの確認間隔           | 3秒  |
| 入力画像の上限                 | 10MB |
| リンクコードの有効期間         | 10分 |

リンクコードは運営者だけが発行し、認証なしで発行できるAPIは作りません。リンクの要求は誰でも送れますが、未知・期限切れ・使用済みのコードを区別せず拒否します。8文字（1兆通り以上）で10分で失効し1回だけ使えるコードは、現実的に推測で当てられないため、リンクに回数制限は付けません。desktop-comfyui-serverのREADMEはIPごとの回数制限を勧めていますが、この理由から採用していません。

ワークフロー定義と勝敗の判定は単体テスト（`scoring-workflows.test.ts`、`battle-progress.test.ts`）、採点ワーカー向けAPIはE2E（`tests/e2e/scoring.spec.ts`）で確認します。提出から勝敗の確定までを通すE2Eは、画像生成の実装後に追加します。
