# 採点の設計

## 目的と対象範囲

2人以上が提出した対戦で、お題に対する提出画像の再現度を採点し、ボーナスを加えた最終スコアで勝敗（3人以上は順位）を確定する仕組みを扱います。勝敗のルールは[ゲーム仕様](product.md#対戦の流れ)、全体の構成は[アーキテクチャ](architecture.md#採点)に従います。採点の実行先とキューの方式を選んだ理由は[ADR 0004](decisions/0004-scoring-workers.md)、採点ワーカーの準備と登録の手順は[CONTRIBUTING.md](../CONTRIBUTING.md#採点ワーカーの準備)を参照してください。

## 用語

| 用語             | 意味                                                                                                                                                     |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 採点ワーカー     | 運営者のPCで動く[desktop-comfyui-server](https://github.com/mintani/desktop-comfyui-server)。Animicへ採点ジョブを取りに来て、ComfyUIで採点した結果を返す |
| 採点ジョブ       | 採点の依頼1件。順番付きの入力画像と、使うワークフローの版を持つ                                                                                          |
| 採点結果         | 採点ジョブから得た参加者ごとの`total`                                                                                                                    |
| 再現度           | 採点結果の`total`。指標ごとの点を重みで平均した0〜100点                                                                                                  |
| ボーナス         | 最速提出ボーナスと最少生成ボーナス。対戦を始めたときの点と対象の下限を使う                                                                               |
| 最終スコア       | 再現度に、取ったボーナスを加えた値。勝敗・順位・戦績に使う                                                                                               |
| リンクコード     | 採点ワーカーを登録するための、10分間有効で1回だけ使えるコード                                                                                            |
| ワークフロー定義 | ワークフローの版ごとに、入力からワークフローJSONを組み立てる処理と、出力から参加者ごとの`total`と指標ごとの点を読む処理                                  |

## 役割と構成

| 配置                                             | 役割                                                                          |
| ------------------------------------------------ | ----------------------------------------------------------------------------- |
| `src/features/scoring/scoring-workers.server.ts` | 採点ワーカー向けAPI。desktop-comfyui-serverの通信仕様との変換、秘密情報の照合 |
| `src/features/scoring/scoring-jobs.server.ts`    | 採点ジョブの登録・割り当て・完了・差し戻しと、ルームのDO向けの状態取得        |
| `src/features/scoring/scoring-workflows.ts`      | ワークフロー定義。今は`illust-similarity-v2`だけを持つ                        |
| `src/features/scoring/final-score.ts`            | ボーナスの値の検証と、再現度とボーナスから最終スコアを求める純粋な関数        |
| `src/features/battle/battle-state.ts`            | 採点エントリーの追加、最終スコアによる勝敗の確定、配信・保存する内容          |
| `src/features/room/room.server.ts`               | 採点待ちの間、Alarmで採点ジョブを登録し、状態と結果を取得して対戦へ反映する   |
| `src/server.ts`                                  | 採点ワーカー向けAPIを、TanStack Startより前に`scoring`へ振り分ける            |

desktop-comfyui-serverの通信仕様で決まっているURLパスとキー名は、`scoring-workers.server.ts`だけに書きます。`scoring`はルームのDOを呼び出さず、DOが`scoring`のサーバー処理を呼び出して結果を受け取ります。

## データと状態

### D1

テーブル定義は`src/features/scoring/scoring.schema.ts`にあります。

| テーブル            | 内容                                                                                                             |
| ------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `scoring_worker`    | 採点ワーカーのID・表示名・秘密情報のSHA-256・最後にheartbeatを受け取った日時と状態・失効日時                     |
| `scoring_link_code` | リンクコード・登録する採点ワーカーの表示名・失効日時                                                             |
| `scoring_job`       | 対戦ID・ルームコード・ワークフローの版・入力・状態・試行回数・割り当て先・割り当ての期限・出力・失敗の理由・重み |
| `scoring_result`    | 採点ジョブと参加者ごとの`total`                                                                                  |
| `scoring_weight`    | 再現度の指標ごとの重み・ボーナスの点と対象の下限・保存した日時。変えるたびに行を足す                             |

採点ジョブのIDは対戦の状態で発行し、登録は冪等にします。登録のときに、対戦を始めた時刻より前に保存した最新の重み（なければ既定値）を`scoring_job`の`weights`へ写します（`src/features/scoring/scoring-weights.server.ts`）。採点ワーカーから受け取った出力は加工せず`raw_result`に保存し、指標ごとの点とジョブの重みから計算した`total`を`scoring_result`に保存します。計算は採点ノードと同じく、点のある指標だけで重みを割り直した加重平均（小数3桁）です（`weightedTotal`）。重みを写す前に登録したジョブは、採点ノードの`total`を使います。戦績の詳細と結果画面のスコアの内訳では、対戦IDと参加者ID（戦績の詳細は本人、結果画面は採点された全員）で成功した採点ジョブを探し（`getScoringMetrics`、`scoring_job`の`battle_id`に索引あり）、`raw_result`から指標ごとの点を読みます。点のない指標（人物のいない画像のCCIP、失敗した指標）は対象外として表示します。指標の表示名は`src/features/scoring/scoring-metrics.ts`にあります。

ボーナスの点と対象の下限は、重みと同じ`scoring_weight`の行に保存します（`speed_bonus`・`generation_bonus`・`bonus_min_similarity`）。ボーナスの列を加える前に保存した行は`null`で、既定値（3点・3点・0点）を使います。ボーナスは採点ジョブには写さず、ルームのDOが対戦を始めるときに、開始時刻より前に保存した最新の値を読んで対戦の状態に記録します。重みとボーナスは同じ開始時刻で引くため、同じ行の値になります。

採点ジョブの状態は次のように変わります。

| 状態                | 次の状態                                                                                                                    |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `queued`            | 採点ワーカーの要求で`running`。試行回数を1増やし、割り当ての期限を2分後にする                                               |
| `running`           | 完了の報告で出力から`total`を計算できれば`succeeded`                                                                        |
| `running`           | 失敗の報告・割り当ての期限切れ・`total`を計算できない出力・画像の取得失敗のとき、試行回数が2未満なら`queued`、2なら`failed` |
| `queued`・`running` | 対戦の結果が確定したら`failed`。採点期限切れや相手の未提出で終わった対戦のジョブを、採点ワーカーへ割り当てない              |
| `succeeded`         | 変わらない                                                                                                                  |
| `failed`            | 変わらない                                                                                                                  |

### 対戦の状態

ルームのDOが保存する対戦の状態に、`scoring`（採点期限と参加者ごとの採点エントリー）と`scoreBonus`（対戦を始めたときのボーナスの点と対象の下限）を持たせます。採点エントリーは提出時に`pending`で追加し、採点ジョブの結果に応じて`succeeded`（`total`付き）か`failed`にします。`scoreBonus`のない保存済みの状態は、ボーナスなし（すべて0）として読みます。

最終スコアは、`succeeded`の採点エントリーと提出の記録（`submittedAt`・`eligibleForSpeedBonus`・`successfulGenerationCount`）から、[ゲーム仕様](product.md#最終スコア)の規則で`computeFinalScores`が求めます。採点エントリーの`total`（再現度）は変えず、勝敗を決めるとき・配信するとき・保存するときに同じ関数で求めます。結果の確定後は採点エントリーを変えないため、どの時点でも同じ値になります。内訳は、ボーナスごとに、その対戦で定義していなければ`null`、定義していて取れなかった人は0です。

結果には、採点による勝ち（`higher-score`）・引き分け（`same-score`）・採点失敗による勝負不成立（`scoring-failed`）を加えます。

- 結果が確定した後は、採点ジョブの結果で対戦の状態を変更しません。
- 対戦の状態にない採点ジョブの結果は反映しません。
- 採点による結果が確定するまで、相手の最終スコアと提出画像を配信しません。確定後は、採点された全員の最終スコアと内訳（`scores[]`の`total`・`similarity`・`speedBonus`・`generationBonus`）、提出の記録（`scores[].submission`）と提出画像を配信します。
- `battle_result`へ保存するJSONの`scores`には、全員の最終スコア（`total`）と内訳（`similarity`・`speedBonus`・`generationBonus`）を含めます。内訳のない前の結果は、`total`を再現度としボーナスなしとして読みます。`battle_record`には最終スコア（`total`）と再現度（`similarity`）を分けて保存します。

## 処理の流れ

1. 参加者が画像を提出すると、`battle`がその提出の採点エントリーを追加し、採点ジョブのIDを発行します。
2. ルームのDOは、採点を待つエントリーがある間、3秒間隔のAlarmで採点ジョブをD1へ登録し、状態と結果を取得して対戦へ反映します。D1との通信に失敗したら、次のAlarmで再試行します。操作が続いても確認を先へ延ばしません。
3. 採点ワーカーがジョブを要求すると、期限切れのジョブを差し戻したうえで、待機中で最も古いジョブを1台だけに割り当てます。入力の順に画像を取得してbase64で渡し、ワークフロー定義で組み立てたワークフローを添えます。このアプリが配信するお題の画像と生成画像は、自分のURLへ通信せずR2から読みます。画像を取得できなければ、その試行を失敗として扱い、ジョブを渡しません。
4. 採点ワーカーが完了を報告すると、出力を保存し、ワークフロー定義で指標ごとの点を読み、ジョブに写した重みで参加者ごとの`total`を計算します。
5. 全参加者の提出状態が確定し、提出者が2人以上で、全員の採点が成功したら、最終スコアを比べて結果を確定します。制限時間の前に全員が提出した場合も、採点がそろった時点で確定します。
6. 2人の対戦では、採点に失敗したエントリーがあるか、全参加者の提出が確定してから5分以内に採点がそろわなければ、勝負不成立とします。3人以上の対戦では、採点に失敗した人と5分以内に採点がそろわなかった人を順位なしにして、残りの人の最終スコアで結果を確定します。順位なしの人はボーナスの対象にしません。全員の採点ができなかった場合は勝負不成立とします。
7. 確定した結果は、既存の仕組みでD1の`battle_result`へ保存します。保存と同じ再試行の中で、保存より先に、その対戦の終わっていない採点ジョブを`failed`にします。結果の確定と同時に採点ジョブの登録が届いた場合も、ルームのDOが登録後に結果を確認して同じように取り消します。採点を待つ間にルームが閉じた場合は、勝負不成立（`room-closed`）として結果を確定し、同じように取り消します。

採点ワーカーの秘密情報は、リンク時に一度だけ返し、D1にはSHA-256だけを保存します。以降の要求はBearerで受け取り、定数時間で照合します。失効日時がある採点ワーカーの要求は拒否します。

## 依存関係

- desktop-comfyui-server 0.4.0の通信仕様: 採点ワーカーがジョブを取りに来る方式、画像のbase64での受け渡し、JSONを返すheartbeat、ジョブがないときの204。
- comfyui-illust-similarity 0.2.0以降の`IllustSimilarityAll`ノード: `similarity`という出力ノードが、5つの指標（CCIP・PixAI Tagger・SigLIP 2・DINOv2・Depth）の点と`total`をJSON文字列で出力します。ノードの`total`は既定の重みで計算した値のため、重みを写したジョブでは使いません。指標と重みは[ゲーム仕様](product.md#対象範囲)のとおりです。
- D1: 採点ジョブ・採点ワーカー・リンクコード・採点結果・採点の重みとボーナスの保存。

## 制約と検証

| 項目                           | 値   |
| ------------------------------ | ---- |
| 割り当ての期限                 | 2分  |
| 採点ジョブの試行回数           | 2回  |
| 採点期限（全員の提出確定から） | 5分  |
| ルームのDOの確認間隔           | 3秒  |
| 入力画像の上限                 | 10MB |
| リンクコードの有効期間         | 10分 |

リンクコードは運営者だけが管理画面（`/admin`）から発行し、認証なしで発行できるAPIは作りません。リンクの要求は誰でも送れますが、未知・期限切れ・使用済みのコードを区別せず拒否します。8文字（1兆通り以上）で10分で失効し1回だけ使えるコードは、現実的に推測で当てられないため、リンクに回数制限は付けません。desktop-comfyui-serverのREADMEはIPごとの回数制限を勧めていますが、この理由から採用していません。

ワークフロー定義・最終スコアの計算・勝敗の判定は単体テスト（`scoring-workflows.test.ts`、`final-score.test.ts`、`battle-progress.test.ts`）、採点ワーカー向けAPIと、生成した画像の提出から勝敗の確定までは、テストが採点ワーカーとして振る舞うE2E（`tests/e2e/scoring.spec.ts`）で確認します。
